# Обязательный чек-лист Код-Ревьюера

> **Назначение:** жёсткий единый чек-лист, который Код-Ревьюер ОБЯЗАН пройти пункт за пунктом при проверке результата исследования (после Исследователя) и feature файла (после Писателя). Без прохождения всех пунктов вердикт ✅ КОРРЕКТЕН выносить ЗАПРЕЩЕНО.
>
> Этот файл является **единственным источником истины** для обоих типов ревью. Все остальные файлы (`Промпт_КодРевьюер_Feature.MD`, `Промпт_КодРевьюер_Исследование.MD`, `ПодготовкаУправляющегоАгента.MD`) ОБЯЗАНЫ ссылаться на этот файл, а не дублировать его содержимое.
>
> Управляющий Агент ОБЯЗАН передать содержимое этого чек-листа субагенту Код-Ревьюеру при каждом запуске (после Шага 1 — Исследователь, и после Шага 4 — Писатель).

---

## Принцип

Ревью считается **пройденным корректно** (✅ КОРРЕКТЕН) только если выполнены **ВСЕ обязательные проверки** ниже. Если хотя бы одна проверка провалена — вердикт **❌ НЕКОРРЕКТЕН** с перечислением конкретных нарушений.

### Статус N/A (неприменимо)

Некоторые пункты проверяют артефакты, которые ещё не созданы на текущем этапе пайплайна. Для таких пунктов используется статус **N/A** (неприменимо):

- **N/A** ставится, когда пункт проверяет артефакт, который физически не существует на момент ревью (например, проверка feature-файла при ревью Researcher — feature ещё не написан Писателем).
- **N/A НЕ считается ни PASS, ни FAIL** — пункт просто исключается из подсчёта.
- Ревьюер ОБЯЗАН явно указать статус N/A с кратким обоснованием: `N/A — <причина>` (например, `N/A — feature-файл ещё не создан Писателем`).
- **ЗАПРЕЩЕНО** ставить N/A без обоснования или использовать N/A как способ «обойти» проверку реально существующего артефакта.

> 📌 **Главное правило:** N/A применяется только к пунктам, проверяющим артефакты, которых ещё нет на данном этапе. Если артефакт существует — пункт проверяется в обычном режиме (PASS/FAIL).

### Какие блоки применять

| Тип ревью | Применяемые блоки |
|-----------|-------------------|
| **Ревью Writer** (после Писателя, проверка feature файла) | **Блок 0**, **A**, **B**, **C**, **E** |
| **Ревью Researcher** (после Исследователя, проверка исследования) | **B**, **D**, **R** |

> Блок 0 — это **machine-check** (программные проверки через `Bash`/`grep`/`mcp__VA__*`). Применяется **только** для ревью Writer, потому что только Writer запускает сценарий через `run_scenario` и может получить `get_test_results`.

## Блок 0. Machine-check (только для ревью Writer)

> ⚠️ **Обязательно выполнить ДО субъективной оценки.** Без выполнения machine-check дальнейший анализ проводить НЕЛЬЗЯ. Если хотя бы одна из этих проверок FAIL — общий вердикт ❌ FEATURE НЕКОРРЕКТЕН, даже если субъективный анализ даёт PASS (перекрёстная проверка).

### 0.1. Загрузка базы знаний

```
get_data_from_knowledge_base(format="all")
```

Сохранить краткое резюме базы знаний (5–7 ключевых правил, которые будут применяться).

### 0.2. Программные проверки через `Bash` (`grep`)

Выполнить следующие проверки и зафиксировать результаты:

```bash
# 1. Наличие DEBUG-комментария
grep -c "^# DEBUG:" "features/<NN>_<ИмяСценария>.feature"

# 2. Наличие language header
grep -c "^# language: ru" "features/<NN>_<ИмяСценария>.feature"

# 3. Подсчёт использований ключевого слова Когда
grep -c "^\s*Когда " "features/<NN>_<ИмяСценария>.feature"

# 4. Подсчёт использований ключевого слова Тогда
grep -c "^\s*Тогда " "features/<NN>_<ИмяСценария>.feature"

# 5. Подсчёт использования # комментариев внутри сценариев (должно быть 0 — используем *)
grep -cE "^\s+# [А-ЯЁ]" "features/<NN>_<ИмяСценария>.feature"

# 6. Подсчёт использования * групп шагов
grep -cE "^\s*\* " "features/<NN>_<ИмяСценария>.feature"

# 7. Подсчёт использования "В панели разделов" (должно быть 0 — должен быть "В командном интерфейсе")
grep -c "В панели разделов" "features/<NN>_<ИмяСценария>.feature"

# 8. Подсчёт использования "В панели функций" (должно быть 0 — должен быть "В командном интерфейсе")
grep -c "В панели функций" "features/<NN>_<ИмяСценария>.feature"

# 9. Поиск запрещённых шагов (Пауза, Я подключаю TestClient)
grep -cE "(Пауза|Я подключаю TestClient)" "features/<NN>_<ИмяСценария>.feature"

# 10. Поиск шага очистки в начале
grep -c "я закрываю все окна клиентского приложения" "features/<NN>_<ИмяСценария>.feature"
```

### 0.3. Проверка синтаксиса через `check_syntax`

```
check_syntax(filePath="<абсолютный_путь_к_feature_файлу>")
```

Зафиксировать:
- Количество ошибок
- Количество предупреждений
- Список ошибок (если есть) — это **автоматический FAIL по пункту C3**

### 0.4. Извлечение результатов запуска через `get_test_results`

```
get_test_results()
```

Зафиксировать:
- Количество шагов Success
- Количество шагов Failed
- Количество шагов Pending
- Общее время выполнения

Если Failed > 0 или Pending > 0 — это **автоматический FAIL по пункту A4** (сценарий не отлажен).

### Интерпретация результатов machine-check

| # | Проверка | Ожидание | Если не так |
|---|----------|----------|-------------|
| 0.1 | DEBUG комментарий (grep #1) | ≥ 1 | ❌ A1 FAIL |
| 0.1 | `# language: ru` (grep #2) | ≥ 1 | ❌ B1 FAIL |
| 0.1 | Когда (grep #3) | ≥ 1 | ❌ B2 FAIL |
| 0.1 | Тогда (grep #4) | ≥ 1 | ❌ E2 FAIL (нет валидации) |
| 0.1 | `# [А-ЯЁ]` внутри сценария (grep #5) | = 0 | ❌ B8 FAIL |
| 0.1 | `* ` группы (grep #6) | ≥ 1 (если многоэтапный) | ⚠️ B9 FAIL |
| 0.1 | «В панели разделов» (grep #7) | = 0 | ❌ B5 FAIL |
| 0.1 | «В панели функций» (grep #8) | = 0 | ❌ B5 FAIL |
| 0.1 | Запрещённые шаги (grep #9) | = 0 | ❌ E5 FAIL |
| 0.1 | «закрываю все окна» (grep #10) | ≥ 1 | ❌ E3 FAIL |
| 0.3 | `check_syntax` | 0 ошибок | ❌ C3 FAIL |
| 0.4 | `get_test_results` | Failed = 0, Pending = 0, Success ≥ 5 | ❌ A4 FAIL |

## Блок A. Проверка реальности запуска сценария (только для ревью Writer)

> ⚠️ **Блок A применяется ТОЛЬКО для ревью Writer** (после Писателя). Пункты A1–A4 проверяют артефакты Писателя: `# DEBUG`-комментарий в feature, лог `writer/`, результаты `get_test_results`. На этапе ревью Researcher (после Исследователя) эти артефакты **ещё не созданы** — Писатель ещё не запускался. Поэтому для ревью Researcher вместо Блока A применяется **Блок R** (реальность UI-исследования).

| # | Проверка | Как проверить | Без выполнения |
|---|----------|---------------|----------------|
| A1 | В начале feature файла есть комментарий `# DEBUG: <N> итераций, <время> сек, последний успешный запуск <дата>` | `Read` первые 5 строк файла или `grep -c "^# DEBUG:"` | ❌ FAIL |
| A2 | Файл лога `writer/ПисательСценариев_<NN>_<Имя>.MD` существует и размер > 3 КБ | `Bash: ls -la writer/...` | ❌ FAIL |
| A3 | В логе Писателя заполнены все 3 обязательных раздела: «🔧 История вызовов инструментов», «📊 Оценка полезности», «⚠️ Проблемы и решения» | `Read` лог | ❌ FAIL |
| A4 | `get_test_results` показывает `Failed = 0`, `Pending = 0` для всех шагов сценария; `Success ≥ 5` | `mcp__VA__get_test_results` | ❌ FAIL |

## Блок R. Реальность UI-исследования (только для ревью Researcher)

> ⚠️ **Блок R применяется ТОЛЬКО для ревью Researcher** (после Исследователя). Заменяет Блок A на этапе исследования: проверяет, что исследование реально выполнено через UI клиента тестирования, а не «выдумано» по косвенным данным. Блок A здесь неприменим, т.к. Писатель ещё не запускался и артефактов запуска сценария (feature, `writer/`, `get_test_results`) не существует.

| # | Проверка | Как проверить | Без выполнения |
|---|----------|---------------|----------------|
| R1 | Клиент тестирования был подключён, сценарий выполнен через реальный UI (не «по памяти» и не по косвенным данным) | `Read` `research/РезультатИсследования_<NN>_<Имя>.MD` — поиск упоминания реального взаимодействия с формами | ❌ FAIL |
| R2 | Запись действий пользователя (`user_actions_recording`) остановлена, Turbo Gherkin сохранён в research-файле | `Read` research-файл — наличие шагов в формате Gherkin | ❌ FAIL |
| R3 | Есть доказательства ключевого результата исследования (скриншоты в `png/`, зафиксированные результаты ветвей сценария, данные элементов формы) | `ls png/`, `Read` research-файл | ❌ FAIL |
| R4 | Состояние формы проверено через данные элемента/объекта (`get_active_window_data`, `get_form_analysis`, `get_object_attributes`, `get_table_data`) — не только визуально | `Read` research-файл — упоминание вызовов инструментов получения данных | ❌ FAIL |
| R5 | Отсутствующие данные и UI-блокировки (скрытые кнопки, недоступные элементы) явно зафиксированы с указанием причины | `Read` research-файл — раздел блокировок | ❌ FAIL |

## Блок B. Проверка соответствия базе знаний Vanessa Automation (общий для Writer и Researcher)

Код-Ревьюер ОБЯЗАН проверить feature файл на соответствие ключевым правилам из базы знаний. Ниже приведены **частые нарушения**, которые приводили к ложным ✅ в прошлом.

> ⚠️ **Применимость пунктов для ревью Researcher:** пункт **B1** проверяет наличие `# language: ru` и заголовков `Функционал:`/`Сценарий:` — это артефакты feature-файла, который на этапе исследования **ещё не создан**. Поэтому для ревью Researcher пункт **B1 = N/A** (feature ещё не написан Писателем). Пункты **B2–B12** применяются для обоих типов ревью: при ревью Researcher они проверяют рекомендации исследования на соответствие базе знаний (оформление Markdown, корректность описания шагов, имён окон и т.п.).

| # | Вопрос БЗ | Правило | Типичное нарушение |
|---|-----------|---------|---------------------|
| B1 | **Q5** | `# language: ru` присутствует; `Функционал:` или `Функциональность:`; `Сценарий:` без подчёркивания в номере; нет конфликтующих имён подсценариев | `Сценарий_1:` вместо `Сценарий:` |
| B2 | **Q5** | Ключевые слова: `Когда`, `И`, `Тогда`, `Дано` — использованы корректно | Произвольные слова (`When`, `Then`, `Given`) |
| B3 | **Q5** | Строковые параметры в апострофах `'...'` (приоритет апострофа) | Строки в кавычках с экранированием |
| B4 | **Q25** | Символ `*` в конце заголовка окна — **без пробела**: `"Заявка (создание)*"`, а НЕ `"Заявка (создание) *"` | `"Заявка (создание) *"` с пробелом |
| B5 | **Q43** ⚠️ | Панель разделов + панель функций — это **ОДИН** шаг: `И В командном интерфейсе я выбираю "Раздел" "Функция"`. **НЕЛЬЗЯ** использовать два отдельных шага `Когда В панели разделов я выбираю ...` + `И В панели функций я выбираю ...` | ❌ Два отдельных шага — НАРУШЕНИЕ |
| B6 | **Q62** | Завершение редактирования строки (`я завершаю редактирование строки`) — вызывается **только после заполнения последнего поля** строки таблицы | Лишний вызов после не последнего поля |
| B7 | **Q96** | Окно списка — **множественное число**: `"Заявки на закупку"`. Форма создания — с суффиксом `(создание)*`: `"Заявка на закупку (создание)*"` | `"Заявка на закупку"` (ед.ч.) для списка |
| B8 | **Q102** ⚠️ | Для логического структурирования сценария использовать `*` группы шагов (сворачиваются в редакторе), а НЕ `#` комментарии | ❌ `#` комментарии вместо `*` групп — НАРУШЕНИЕ |
| B9 | **Q35** | Группировка шагов рекомендуется для многоэтапных сценариев | Один плоский список шагов без структуры |
| B10 | **Q22** | Нет лишних шагов `я активизирую поле` — они остаются после накликивания и снижают читабельность | `И в таблице "X" я активизирую поле "Y"` без необходимости |
| B11 | **Q1** | Кнопки искать по **имени** (`с именем 'X'`), а не по заголовку | `И я нажимаю на кнопку 'Заголовок'` (когда можно по имени) |
| B12 | **Q23** | После смены окон — ожидание открытия (`Тогда открылось окно "..."`) | Шаги идут подряд без проверки окна |

## Блок E. Дополнительные проверки feature-файла (только для ревью Writer)

| # | Проверка | Как проверить | Без выполнения |
|---|----------|---------------|----------------|

## Алгоритм вынесения вердикта

```
ПОЛУЧИТЬ знания (get_data_from_knowledge_base, format=all) — обязательно

ЕСЛИ ревью Writer:
    ВЫПОЛНИТЬ machine-check (Блок 0) — обязательно ДО субъективной оценки
    ДЛЯ КАЖДОГО блока A, B, C, E:
        Проверить ВСЕ пункты блока
        ЕСЛИ хотя бы один пункт FAIL:
            Вердикт = ❌ НЕКОРРЕКТЕН
            Перечислить КОНКРЕТНЫЕ нарушения с указанием строк в feature файле
            Сохранить результат в rewiew/<...>_Writer_<N>.MD
            ВЫЙТИ
ИНАЧЕ (ревью Researcher):
    ДЛЯ КАЖДОГО блока B, D, R:
        Проверить ВСЕ пункты блока
        (пункты, проверяющие несуществующие артефакты, — N/A с обоснованием;
         N/A не считается FAIL)
        ЕСЛИ хотя бы один пункт FAIL:
            Вердикт = ❌ НЕКОРРЕКТЕН
            Перечислить КОНКРЕТНЫЕ нарушения с указанием строк в research файле
            Сохранить результат в rewiew/<...>_Researcher_<N>.MD
            ВЫЙТИ

ЕСЛИ все пункты всех применимых блоков PASS (или N/A, ни одного FAIL):
    Вердикт = ✅ КОРРЕКТЕН
    Сохранить результат в rewiew/<...>.MD
```

## Критическое правило

**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** выносить вердикт `✅ КОРРЕКТЕН`, если:
- Не вызван `get_data_from_knowledge_base(format=all)` **до** начала ревью
- Для ревью Writer: не выполнены ВСЕ пункты блока 0 (machine-check) и блока A (реальность запуска)
- Для ревью Researcher: не пройдены все пункты блоков B, D и R (соответствие БЗ + содержание исследования + реальность UI-исследования)
- Не пройдены все пункты блока B (соответствие базе знаний)
- Любое нарушение помечено как «⚠️ НАРУШЕНИЕ» в таблице выше (B5, B8)

## Шаблон записи в файле ревью

Каждый файл `rewiew/rewiew_<NN>_<Имя>_<Тип>_<N>.MD` ОБЯЗАН содержать результаты прохождения чек-листа в формате:

```markdown
## ✅ Прохождение обязательного чек-листа

### Machine-check (только Writer)
- [x] 0.1. grep DEBUG, language, Когда, Тогда, группы, панели — PASS
- [x] 0.2. check_syntax — 0 ошибок
- [x] 0.3. get_test_results — 0 Failed, 0 Pending, N Success

### Блок A. Реальность запуска
- [x] A1. DEBUG-комментарий присутствует
- [x] A2. Файл лога существует
- [x] A3. Все 3 раздела заполнены
- [x] A4. get_test_results: 0 Failed, 0 Pending

### Блок B. Соответствие базе знаний
- [x] B1. # language: ru, Функционал:, Сценарий:
- [x] B2. Корректные ключевые слова
- [x] B3. Строки в апострофах
- [x] B4. * без пробела в конце заголовков окон
- [ ] B5. Панель разделов/функций — ОДИН шаг ⚠️ НАРУШЕНИЕ: строки 16-17 используют два отдельных шага
- [x] B6. Завершение редактирования — после последнего поля
- [x] B7. Множественное число для списков, (создание)* для формы создания
- [ ] B8. * группы шагов вместо # комментариев ⚠️ НАРУШЕНИЕ: строки 12, 15, 20-22 используют #
- [x] B9-B12. ...

### Блок C/D/E (в зависимости от типа ревью)
- [x] Все пункты PASS

## 📤 Вердикт
❌ НЕКОРРЕКТЕН — 2 нарушения (B5, B8)
```
