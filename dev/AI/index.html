    MCP в Vanessa Automation¶

    Быстрый старт¶

    Для начала использования MCP в Vanessa Automation выполните следующие шаги:

    1. Настройте LLM с поддержкой MCP. У вас должна быть работающая LLM, к которой можно подключить MCP инструменты. Например, VSCode + плагин Cline — это среда, где вы пишете промты.

    2. Установите расширение в базу менеджера тестирования. В базу менеджера тестирования необходимо поставить расширение из проекта.

    3. Запустите MCP сервер. Нажмите на кнопку Запустить в расширении.

    4. Настройте MCP клиент в вашей IDE. В вашей IDE, где работает LLM, необходимо прописать настройки MCP сервера, который запущен в менеджере тестирования. В инструкции ниже приведены примеры настроек для плагина Continue (для VSCode), плагина Cline и плагина Roo Code (тоже для VSCode).

    5. Включите внешнюю компоненту VanessaExt. В Vanessa Automation необходимо включить использование внешней компоненты VanessaExt.

    6. Установите расширение VAExtension. В базу клиента тестирования необходимо добавить расширение VAExtension.

    7. Настройка завершена. После выполнения всех шагов MCP готов к работе.

    Пример запуска сеанса 1С из командной строки так, чтобы сразу запустился MCP сервер¶

    "C:\Program Files\1cv8\8.3.27.2130\bin\1cv8c.exe" ENTERPRISE /TESTMANAGER /IBConnectionString "File=""c:\Bases\8.3.27"";" /Execute "C:\Commons\rep\vanessa-automation\vanessa-automation.epf" /C "runMcp;mcpPort=9876"

    🚀 Реальный проект покрытия тестами¶

    Файлы из examples/МультиАгент/ — это шаблоны. Для покрытия тестами конкретной конфигурации 1С создаётся реальный проект — отдельный каталог, в котором лежат копии шаблонов и проектные данные.

    📂 Структура реального проекта¶

    <корень_проекта>/
├── ТестПлан.MD                  ← Вход: тесты в свободной форме (Дано/Когда/Тогда)
├── ТестПлан.pdf                 ← PDF-версия для согласования (опционально)
├── ПараметрыКонфигурации.MD     ← Пути к DT, исходникам, профилю (ОБЯЗАТЕЛЬНО)
│
├── InstructionsResearch.md       ← Копия шаблона
├── InstructionsWriteScenario.md ← Копия шаблона
├── ПодготовкаУправляющегоАгента.MD ← Копия шаблона
│
├── ПромптыСубагентов/           ← Копии промптов субагентов
│
├── Чеклисты/                    ← Чек-листы для ревьюеров
│   └── *.MD
│
├── dt/                          ← DT-эталон и лог restore
│   ├── <Эталон>.dt
│   └── log.txt
│
├── data/                        ← Выход: анализ командного интерфейса
│   └── АнализДанных_<NN>_<...>.MD
│
├── research/                    ← Выход: результаты исследования
│   └── РезультатИсследования_<NN>_<...>.MD
│
├── features/                    ← Выход: готовые feature-файлы
│   └── <NN>_<КраткоеНазвание>.feature
│
├── rewiew/                      ← Выход: отчёты ревьюеров
│   ├── rewiew_<NN>_<...>_Researcher_<N>.MD
│   └── rewiew_<NN>_<...>_Writer_<N>.MD
│
├── restore/                     ← Выход: отчёты о восстановлении базы
│   └── Restore_<NN>_<...>.MD
│
├── writer/                      ← Выход: логи работы Писателя
│   └── ПисательСценариев_<NN>_<...>.MD
│
├── png/                         ← Скриншоты (создаются при отладке)
│
└── Архив/                       ← Старые/неактуальные файлы

    🔄 Полный workflow от ТестПлан.MD до готовых feature-файлов¶

    ВХОДЫ (пользователь):
├── ТестПлан.MD           — тесты в свободной форме
├── dt/<Эталон>.dt        — эталонное состояние базы
└── ПараметрыКонфигурации.MD — пути проекта

         ↓

УПРАВЛЯЮЩИЙ АГЕНТ (оркестратор):
1. Парсит ТестПлан.MD → СПИСОК_СЦЕНАРИЕВ
2. Для каждого сценария запускает цепочку субагентов

         ↓

ВЫХОДЫ (по каждому сценарию):
├── data/АнализДанных_<NN>.MD            ← от АнализДанныхИИнтерфейса
├── research/РезультатИсследования_<NN>.MD ← от Исследователя
├── rewiew/rewiew_<NN>_Researcher.md     ← от Код-Ревьюера (Researcher)
├── features/<NN>_<...>.feature         ← от Писателя
├── rewiew/rewiew_<NN>_Writer.md         ← от Код-Ревьюера (Writer)
├── restore/Restore_<NN>.MD             ← от АдминистраторБазы
└── writer/ПисательСценариев_<NN>.MD    ← лог работы Писателя

         ↓

НАКОПЛЕНИЕ ЗНАНИЙ:
└── Memory.MD  ← по итогам работы сюда записываются
                  новые знания о конфигурации

    📋 Шаги для запуска нового тестового проекта¶

    1. Создать каталог проекта (например, C:\Commons\rep\AI\testERP7\).
    2. Скопировать шаблоны из examples/МультиАгент/:
    3. InstructionsResearch.md
    4. InstructionsWriteScenario.md
    5. ПодготовкаУправляющегоАгента.MD
    6. ПромптыСубагентов/ (целиком)
    7. Чеклисты/ (целиком)
    8. Создать ПараметрыКонфигурации.MD и заполнить пути.
    9. Подготовить DT-эталон — положить в dt/<Эталон>.dt.
    10. Написать ТестПлан.MD — заполнить тесты в свободной форме.
    11. Запустить Управляющего Агента (см. ПодготовкаУправляющегоАгента.MD).

    🔗 Связь между шаблонами и реальным проектом¶

    Шаблон (examples/МультиАгент/) Копия в реальном проекте Отличия
    ПодготовкаУправляющегоАгента.MD копируется обычно без изменений
    InstructionsResearch.md копируется может дополняться под конфигурацию
    InstructionsWriteScenario.md копируется обычно без изменений
    ПромптыСубагентов/*.MD копируются в ПромптыСубагентов/ обычно без изменений
    ПараметрыКонфигурации.MD (шаблон) создаётся в проекте заполняется конкретными путями
    ТестПлан.MD (шаблон) создаётся в проекте заполняется тестами
    — dt/, data/, features/ и т.п. создаются автоматически

    ⚠️ Что НЕ нужно менять¶

    • Шаблоны промптов уже универсальны — они читают ПараметрыКонфигурации.MD и ТестПлан.MD из текущего каталога проекта.
    • ПодготовкаУправляющегоАгента.MD универсален — он парсит ТестПлан.MD и запускает субагентов.
    • Memory.MD пуст при старте и наполняется по ходу работы.

    📚 Дополнительные ресурсы¶

    В директории docs/AI/ расположены вспомогательные файлы, которые содержат важную информацию для работы с MCP в Vanessa Automation.

    📝 ОписаниеЗадачи.md¶

    Путь: examples/ЗапускаемПромптыВРучную/ОписаниеЗадачи.md

    Назначение: Пример оформления задания для ИИ-агента

    Что содержит: - 🎯 Пример формулировки контекста задачи - 📋 Пример структурирования требований к тесту - ✅ Пример оформления проверок и ожидаемых результатов

    Как использовать: 1. При постановке задачи — используйте как шаблон для оформления требований к сценарию 2. Для обучения — изучите структуру и формат описания задач 3. При создании новых задач — адаптируйте пример под свои потребности, сохраняя общую структуру

    📋 1.Исследование.md¶

    Путь: examples/ЗапускаемПромптыВРучную/1.Исследование.md

    Назначение: Промт, который запускает работу исследователя, который выполняет требования к задаче "вручную" и собирает информацию.

    📋 2.Сценарий.md¶

    Путь: examples/ЗапускаемПромптыВРучную/2.Сценарий.md

    Назначение: Промт, который запускает работу по написанию и отладке сценария.

    📋 InstructionsResearch.md¶

    Путь: examples/ЗапускаемПромптыВРучную/InstructionsResearch.md

    Назначение: Подробное руководство по работе исследователя.

    Что содержит: - 📘 Общие вводные и подготовку к работе - 🔧 Включение и остановку записи действий пользователя - 📝 Выполнение будущего сценария тестирования "вручную" - ✅ Сбор информации о реквизитах формы, командном интерфейсе, окнах клиента тестирования, которая потом будет использована для написания и отладки сценария - ✅ Получение примерного сценария на языке Turbo Gherkin, который потом будет использован для написания и отладки сценария

    📋 InstructionsWriteScenario.md¶

    Путь: examples/ЗапускаемПромптыВРучную/InstructionsWriteScenario.md

    Назначение: Подробное руководство по созданию сценариев тестирования для ИИ агента с использованием MCP инструментов.

    Что содержит: - 📘 Общие вводные и подготовку к работе - 🔧 Предварительные действия перед запуском сценариев - 📝 Требования к структуре и форматированию сценариев - 🚨 Алгоритм обработки ошибок - ✅ Чек-лист перед запуском и завершение работы по написанию сценария

    📋 ПараметрыКонфигурации.MD¶

    Путь: examples/МультиАгент/ПараметрыКонфигурации.MD

    Назначение: Файл с путями проекта (DT-эталон, исходники конфигурации, имя профиля клиента тестирования и т.п.). Все субагенты читают этот файл в начале работы.

    Как использовать: 1. Скопировать в корень реального проекта покрытия тестами. 2. Заполнить параметры (путь к DT, путь к исходникам, имя профиля). 3. Субагенты АдминистраторБазы и АналитикКода автоматически будут использовать значения из этого файла.

    Параметры: - Имя проекта - Имя профиля клиента тестирования - Путь к DT-эталону - Путь к лог-файлу restore - Путь к платформе 1С - Путь к базе клиента тестирования - Имя пользователя 1С - Путь к исходникам конфигурации - Имя тестируемой конфигурации

    📋 Чеклисты/¶

    Путь: Создаётся в корне реального проекта

    Назначение: Чек-листы для Код-Ревьюера (и других субагентов), которые формализуют критерии проверки.

    Как использовать: - Передаются Код-Ревьюеру при каждой итерации проверки. - Содержат блоки критериев (A, B, C, D) и правила вынесения вердикта.

    💾 Memory.MD¶

    Путь: examples/ЗапускаемПромптыВРучную/Memory.MD

    Назначение: Файл для хранения накопленного опыта тестирования.

    Что содержит: - Универсальные знания об особенностях тестирования конкретной конфигурации - Паттерны решения типовых задач - Рекомендации по избежанию распространённых ошибок

    Как использовать: 1. Перед созданием сценариев — прочитайте файл для загрузки накопленного опыта 2. После выполнения задачи — сохраните в этот файл новые знания, если они были получены в процессе работы 3. При возникновении проблем — проверьте, есть ли в файле рекомендации по вашей ситуации

    🤖 Многоагентный режим покрытия тестами¶

    Для сложных задач используется многоагентная система, описанная в examples/МультиАгент/ПодготовкаУправляющегоАгента.MD.

    Цепочка субагентов для каждого сценария¶

    [Пользователь] → ТестПлан.MD
        ↓
Управляющий Агент (парсит ТестПлан, итерирует по сценариям)
        ↓
1. АнализДанныхИИнтерфейса → data/АнализДанных_<NN>.MD
        ↓
2. Исследователь → research/РезультатИсследования_<NN>.MD
        ↓
3. Код-Ревьюер (Researcher) → rewiew/rewiew_<NN>_Researcher.md
        ↓ (если ✅)
4. Писатель → features/<NN>_<...>.feature
        ↓
5. Код-Ревьюер (Writer) → rewiew/rewiew_<NN>_Writer.md
        ↓ (если ✅)
6. ✅ Готово!
        ↓ (следующий сценарий)
7. АдминистраторБазы → restore/Restore_<NN>.MD

    🔗 Рекомендуемый порядок работы с файлами¶

    Для простого случая (1-2 сценария)¶

    ТестПлан.MD (ввод теста в свободной форме)
        ↓

    Доступные инструменты:¶

    Ниже приведена таблица всех доступных MCP инструментов Vanessa Automation, отсортированная по имени инструмента.

    Инструмент Описание
    check_syntax Проверяет синтаксис Gherkin в указанном feature-файле. Параметр filePath обязателен. Возвращает Markdown с найденными ошибками: неизвестные шаги, структурные проблемы, ошибки ключевых слов.
    close_test_client Закрывает сеанс клиента тестирования по имени профиля. Если профиль не указан — закрывает текущий подключенный профиль. Используйте для завершения работы с клиентом тестирования после выполнения тестов.
    execute_feature_step Выполняет шаг из .feature файла по номеру строки. Валидирует что файл открыт в редакторе, активирует вкладку при необходимости.
    execute_form_actions Выполняет последовательность действий с элементами формы клиента тестирования. Позволяет выполнить несколько действий за один вызов инструмента. Параметр actions_json (обязательный) - JSON-строка с массивом действий. Каждое действие в массиве содержит: action - тип действия (click_button, input_text, и т.д.), element_name - имя элемента формы, table_name - имя таблицы (если элемент в таблице), value - значение для ввода/выбора, другие параметры в зависимости от действия. При возникновении ошибки выполнение прерывается. Требует подключённого клиента тестирования.
    frequently_used_steps Возвращает информацию о том какие шаги чаще используются по статистике больших проектов. В начале идут часто используемые шаги, далее идут более редко используемые шаги. Возвращает представление шага, описание шага, тип шага. Также возвращает информацию сколько всего шагов есть в накопленной статистике.
    get_active_window_data В зависимости от параметра type возвращает важные свойства активного окна клиента тестирования: если type=window_caption - возвращает самое важное значение активного окна: его заголовок. По заголовку окна можно найти окно и получить его данные, можно активизировать окно, можно закрыть окно. Если type=navigation_link - возвращает навигационную ссылку активного окна. Навигационная ссылка потом может быть использована для открытия окна по навигационной ссылке. Также навигационная ссылка помогает понять с каким объектом метаданных связано активное окно. Если type=form_name - возвращает имя формы, подчиненной активному окну. Имя формы позволяет понять с каким объектом метаданных связано активное окно, т.к. в имени формы чаще всего содержится имя объекта метаданных. Если type=form_caption - возвращает заголовок формы, подчиненной активному окну. Чаще всего такой заголовок формы совпадает с заголовком окна-владельца и он нужен редко.
    get_data_from_knowledge_base Получает информацию из базы знаний, в которой хранится информация о часто возникающих вопросах и как их решить. Данные в базе знаний хранятся в формате Вопрос - ответ. Чтобы экономить токены можно получать данные порциями. Можно получить только тексты вопросов, чтобы потом получить ответ только на нужный вопрос. Можно выполнить поиск по вопросам и ответам. Поиск работает без учёта регистра букв.
    get_editor_state Возвращает состояние Monaco-редактора Vanessa Automation: открытые вкладки, содержимое активного документа, позицию курсора, ошибки. Один вызов для полного понимания контекста редактора. Если feature файл загружен в редактор Vanessa Automation, то уже можно запускать его сценарии на выполнение с помощью run_scenario.
    get_environment_data Получает важные данные об окружении: текущая дата и время, версия платформы 1С:Предприятие, данные об операционной системе, какая используется VA - обычная или Single, включено ли использование внешней компоненты VanessaExt, в какой базе запущен менеджер тестирования.
    get_extension_list Получает список всех расширений установленных в клиент тестирования. Клиент тестирования должен быть подключен. Возвращает информацию о каждом расширении. Поля: Имя, Версия, Назначение; Флаги: Активно, БезопасныйРежим.
    get_form_analysis Возвращает информацию о текущей форме тестируемого приложения: дерево элементов или состояние формы как Gherkin-шаги. Требует подключённого клиента тестирования. Важно обращать на флаг Видимости у элемента формы и групп, в которые он входит. Если у элемента Видимость=Истина, а у группы Видимость=Ложь, то скорее всего элемент формы не виден пользователю и он не может с ним взаимодействовать.
    get_form_element_data Получает данные указанного элемента формы клиента тестирования. Возвращает информацию об элементе в формате Markdown: Имя элемента, Заголовок, Тип, Вид, Значение, Представление (если применимо), Флаги: Видимость, Доступность, ТолькоПросмотр. Параметр element_name обязателен и должен содержать имя элемента формы.
    get_info_about_line_scenario Получает подробную информацию о указанной строке файла открытого в редакторе. Если в строке находится шаг сценария, то будет возвращена подробная информация о шаге.
    get_object_attributes Получает значения реквизитов объекта (и их тип), связанного с открытой формой. Работает только для форм объектов (Справочники, Документы и т.п.), не работает для форм списков и служебных форм. Параметр data_mode определяет состав возвращаемых данных: all (все данные - реквизиты шапки и все табличные части), attributes_only (только реквизиты шапки), single_attribute (только значение указанного реквизита шапки, требуется attribute_name), tabular_sections_only (только все табличные части), single_tabular_section (только указанная табличная часть, требуется tabular_section_name). Параметр only_filled определяет фильтровать ли пустые реквизиты: true (только заполненные), false (все реквизиты, по умолчанию). Параметр не применяется при получении одного реквизита (data_mode='single_attribute'). Возвращает данные в формате Markdown с именами, типами и значениями реквизитов.
    get_table_data Получает данные из таблицы базы данных. Цель - понять какие тестовые данные уже есть в базе, чтобы лучше понимать какими данными заполнять объекты в тестах. Нужно указать Тип - object_type: 1 = Справочник, 2 = Документ, 3 = Перечисление, 4 = одна константа, 5 = все константы, 6 = Реквизиты объекта по навигационной ссылке, 7 = План видов характеристик, 8 = все справочники, 9 = все документы, 10 = все перечисления, 11 = все планы видов характеристик. Надо указать Вид - object_name (обязательный параметр для object_type 1-4 и 7). limit - сколько элементов возвращать (необязательный, по умолчанию 10). Для справочников будет возвращено Наименование, Код, Владелец, если такие поля есть у данного вида справочника. Если справочник подчинен другому справочнику, то должен быть параметр для указания владельца. Для документа будут возвращены Дата, Номер. Для справочников и документов будет также возвращена навигационная ссылка. Для документов можно передать date_start и date_end (оба необязательные, формат: "30.12.2025 15:45:55"). name_filter - отбор по наименованию элемента. Работает для Справочников и Планов видов характеристик. Необязательный параметр. Нужен, чтобы проверить есть ли конкретный элемент в базе. name_match_type - режим сравнения для name_filter: exact (точное совпадение, по умолчанию), partial (частичное совпадение, подстрока в любом месте наименования), starts_with (наименование начинается со значения). Работает только совместно с name_filter. Необязательный параметр. navigationLink - навигационная ссылка на элемент справочника или документ (используется когда object_type = 6). start_number - начальный номер константы в диапазоне (1-based, используется только при object_type = 5). end_number - конечный номер константы в диапазоне (1-based, используется только при object_type = 5). Для планов видов характеристик (object_type = 7) возвращаются Наименование, Код, если такие поля есть у данного вида ПВХ, а также навигационная ссылка. Для справочников, документов и планов видов характеристик в ответе дополнительно возвращается общее количество элементов/документов в информационной базе (без учёта фильтров и параметра limit). object_type = 8 - возвращает список имён всех справочников в базе. object_type = 9 - возвращает список имён всех документов в базе. object_type = 10 - возвращает список имён всех перечислений в базе. object_type = 11 - возвращает список имён всех планов видов характеристик в базе.
    get_test_results Подробные результаты выполнения сценария: статус каждого шага, время, ошибки. Если scenarioId не указан — результат последнего сценария.
    get_vanessa_automation_state Возвращает текущее состояние Vanessa Automation в формате Markdown: выполняется ли сценарий, текущая фича (имя, путь, язык, теги), текущий сценарий (имя, статус, теги), текущий шаг (текст, значения параметров, номер строки), подключен ли клиент тестирования. Используйте для получения контекста перед написанием или анализом тестов.
    get_window_list_os Возвращает список окон доступных для снятия скриншота с точки зрения операционной системы. Нужно вызвать перед get_window_screenshot_os.
    get_window_list_testclient Получает список внутренних окон клиента тестирования. Результат можно использовать для управления окнами с помощью инструмента window_management (активизировать, закрыть, открыть навигационную ссылку), либо для получения данных из текущего окна get_active_window_data. Результат нельзя использовать для получения скриншота окна, т.к. список внутренних окон клиента тестирования и список окон с точки зрения операционной системы - это разные вещи.
    get_window_screenshot_os Делает скриншот окна клиента тестирования и возвращает изображение, для последующего анализа скриншота с помощью компьютерного зрения. Параметр window_title определяет с какого окна нужно снять скриншот, т.к. у одного клиента тестирования может быть несколько окон. Параметр обязательный. Чтобы получить список доступных окон для снятия скриншота надо вызвать get_window_list_os. Параметр color_mode определяет режим цвета: grayscale (черно-белый, по умолчанию) или color (цветной). Если клиент тестирования не подключён или не запущен, возвращает ошибку с подсказкой сначала вызвать manage_test_client с action: connect.
    load_features Загружает или перезагружает .feature файлы. Используйте после того как вы отредактировали .feature файл, чтобы перечитать файл с диска в Vanessa Automation. Это лучший способ перезагрузить текущий файл в редакторе не указывая имя файла.
    manage_breakpoints Управление точками останова в Gherkin-сценариях. Действия: toggle (по умолчанию), remove_all, list.
    manage_command_interface Универсальный инструмент для работы с командным интерфейсом 1С:Предприятия. Поддерживаемые действия (параметр action): get_section_panel - получить панель разделов (первый уровень), get_function_panel - получить панель функций (второй уровень, у функций есть навигационная ссылка, которую потом можно использовать для прямого вызова функции), click_section_panel - нажать кнопку панели разделов (после этого действия появится панель функций данного раздела и интерфейс клиента тестирования будет заблокирован, пока не будет выбрана команда из панели функций), click_function_panel - нажать кнопку панели функций (после нажатия на кнопку панели функций нужно проверить, что открылось нужное окно клиента тестирования с помощью инструмента get_window_list_testclient), close_function_panel - закрыть панель функций, если она открыта (если панель функций не была открыта, просто возвращает сообщение о том, что панель функций не была открыта), get_all - получить весь командный интерфейс (панель разделов и для каждой кнопки панель функций). Для click_section_panel: command (обязательно) - имя кнопки для нажатия, returnFunctionPanel (необязательно) - вернуть содержимое панели функций после нажатия. Для click_function_panel: command (обязательно) - имя кнопки для нажатия, group (необязательно) - имя группы, если команды не уникальны.
    manage_form_elements Универсальный инструмент для управления элементами формы клиента тестирования. Поддерживаемые действия (параметр action): click_button - нажатие на кнопку формы (требуется element_name), input_text - ввод текста в поле (требуются element_name и value), open_dropdown - открыть выпадающий список (требуется element_name), get_dropdown_state - получить состояние открытого списка (требуется element_name), select_from_dropdown - выбрать значение из открытого списка (требуются element_name и value), set_value - установить значение в поле одним действием (требуются element_name и value), open_choice_form - открыть форму выбора для поля (требуется element_name), set_radio_button - установить переключатель (требуется element_name, имеет смысл только для полей шапки), set_checkbox - установить флаг (требуется element_name), unset_checkbox - снять флаг (требуется element_name), toggle_checkbox - переключить флаг на противоположное значение (требуется element_name), click_hyperlink - нажать гиперссылку (требуется element_name, опционально hyperlink_title или hyperlink_index, имеет смысл только для полей шапки), simulate_tab - эмуляция перехода TAB (без параметров или с tab_direction), activate_column - активизировать колонку таблицы (требуются table_name и value=column_name), navigate_next_column - переход к следующей колонке в таблице (эмуляция TAB, параметры: table_name), navigate_previous_column - переход к предыдущей колонке в таблице (эмуляция SHIFT+TAB, параметры: table_name), start_edit_row - начать редактирование строки таблицы (параметры: table_name, редактирование начнётся в текущей колонке таблицы), end_edit_row - закончить редактирование строки таблицы (параметры: table_name), navigate_to_row - переход к строке таблицы по ключу (параметры: table_name и row_criteria в формате 'Колонка=Значение;Колонка2=Значение2'), navigate_next_row - переход к следующей строке таблицы (параметры: table_name), navigate_previous_row - переход к предыдущей строке таблицы (параметры: table_name), select_row - выбрать текущую строку таблицы (эмуляция нажатия ENTER на текущей строке и колонке таблицы, параметры: table_name), get_selected_rows - вернуть значение выделенных строк таблицы (по умолчанию возвращается значение текущей строки, параметры: table_name), create_new - вызывает команду создания нового элемента у указанного поля шапки или поля таблицы (параметры: element_name обязательный, table_name опционально если элемент находится в таблице), switch_tab - переключиться на закладку (группу формы, параметры: element_name имя группы/закладки), toggle_group - развернуть/свернуть группу (параметры: element_name имя группы, value expand/collapse/toggle), activate_header_element - активизировать элемент шапки формы (параметры: element_name), clear_field - очистить поле (требуется element_name, опционально table_name для полей в таблицах), clear_message_window - очистить окно сообщений пользователю в текущем окне (не требует параметров), select_from_form_dropdown - выбрать значение из списка выбора формы (требуются только value). Для элементов в таблицах используйте параметр table_name. Требует подключённого клиента тестирования.
    manage_test_client Управляет клиентом тестирования 1С. Используйте action='connect' с profileName для подключения клиента тестирования. Используйте action='disconnect' для отключения текущего клиента тестирования. При это profileName указывать не обязательно.
    manage_test_client_profiles Универсальный инструмент для работы с таблицей профилей клиентов тестирования Vanessa Automation. Поддерживаемые действия (параметр action): get_list - получить список всех профилей клиентов тестирования, add - добавить новый профиль в таблицу, edit - редактировать существующий профиль. Для add и edit: name (обязательно) - имя профиля, synonym - синоним профиля, infobase_path - строка подключения к базе, additional_parameters - дополнительные параметры подключения, client_type - тип клиента (Тонкий (основной вариант), Толстый, Web, МобильныйКлиент, МобильноеПриложение, МобильныйКлиентАвтономный, ОбычноеПриложение), computer_name - имя компьютера. Уточнение. Если параметры клиента тестирования изменились, то это может потребовать перезапуска клиента тестирования. Подробная информация про то как устроена таблица клиентов тестирования есть в базе знаний, инструмент get_data_from_knowledge_base.
    manage_variables Чтение, установка и удаление переменных тестового контекста. Действия с переменными: get (по умолчанию), set, delete. Переменные позволяют хранить произвольные значения в памяти Vanessa Automation. Переменные бывают локальные и глобальные. Локальные существуют только во время выполнения сценария. Перед началом выполнения сценария все локальные переменные удаляются. Глобальные переменные существуют пока работает Vanessa Automation и не удаляются перед выполнением сценария.
    open_feature_file Открывает .feature файл в Vanessa Editor или активирует уже открытую вкладку. Параметр filePath обязателен. Используйте перед check_syntax, execute_feature_step и ручной навигацией по редактору.
    run_scenario Запускает выполнение сценариев. Отправляет прогресс по каждому шагу (step N/M). Возвращает итоговый результат после завершения. Если указан filePath — загрузит фичу, откроет в редакторе и запустит. Режимы: all (по умолчанию — все сценарии. Если просят выполнить все сценарии надо использовать режим all), reloadAndRun (перезагрузить и запустить фича файл с начала), selected (выбранный в редакторе, перед этим надо вызвать select_scenario), fromCurrentStep (с текущего шага, перед этим нужно вызвать select_step), reloadAndRunFromLine (перезагрузить фича файл и выполнить сценарий со строки указанной в lineNumber).
    save_table_document_to_file Сохраняет содержимое табличного документа в файл на диске. Поддерживаемые форматы: mxl (MXL), xlsx (Excel), pdf (PDF). Параметр file_name обязателен и должен содержать полный путь к файлу. Параметр format необязательный, по умолчанию mxl. Параметр form_element_name обязателен и должен содержать имя элемента формы (табличного документа) для сохранения.
    search_for_steps_by_keywords Ищет шаги Vanessa Automation по переданной строке поиска и возвращает их в формате Markdown. Поиск производится по: представлению шагов, описании шагов и типу шагов. В любой параметр можно передавать несколько значений, разделенных вертикальной чертой |. Пример поиска шагов в представлении которых встречается слово "кнопка": search_name = "кнопка|кнопки|кнопку". Пример исключения шагов в представлении которых встречается слово "поле": exclude_name = "поле|поля". Пример поиска шагов в описании которых встречается слово "клиент тестирования": search_description = "клиент тестирования". Пример исключения шагов в описании которых встречается слово "гиперссылка": exclude_description = "гиперссылка|гиперссылки". Пример поиска шагов в типе которых встречается строка "Объекты конфигурации": search_type = "Объекты конфигурации". Пример исключения шагов в описании которых встречается строка "Переменные среды": exclude_type = "Переменные среды".
    select_scenario Делает сценарий текущим по его имени.
    select_step Делает шаг текущим по номеру строки.
    stop_scenario Посылает команду Vanessa Automation, что нужно остановить выполнение сценариев. На обработку команды может понадобится время.
    user_actions_recording Управляет записью действий пользователя в клиенте тестирования. Поддерживаемые действия (параметр action): start (по умолчанию) - начать запись действий пользователя, stop - остановить запись и вернуть записанные шаги в формате Turbo Gherkin (если после вызова stop нужно опять начать запись действий - то нужно вызвать инструмент с параметром start). При остановке записи возвращается текст шагов в формате Turbo Gherkin, которые были выполнены пользователем за время записи. Требует подключённого клиента тестирования.
    voice_notification Воспроизводит голосовое уведомление через внешнюю компоненту VanessaExt. Полезно в тех случаях, если ИИ агент работает в отдельной виртуальной машине, выполняет какое-то длинное задание и пользователю удобно получать голосовое уведомление о: задании выполненном, необходимости принять решение, задании, которое не может быть выполнено, или ошибке при выполнении задания.
    window_management Универсальный инструмент для управления окнами клиента тестирования. Поддерживаемые действия (параметр action): activate - активизировать окно по заголовку (требуется window_title), close - закрыть окно по заголовку или части заголовка (требуется window_title), open_navigation - открыть навигационную ссылку (требуется navigation_link). Для активизации окна: укажите action='activate' и window_title с полным заголовком окна или используйте символы * для поиска по частичному совпадению (например, 'Окно'). Для закрытия окна: укажите action='close' и window_title (можно часть заголовка для поиска или используйте символы * для поиска по частичному совпадению). Для открытия формы: укажите action='open_navigation' и navigation_link с навигационной ссылкой.
