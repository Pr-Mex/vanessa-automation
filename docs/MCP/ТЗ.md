# MCP-инструменты для Vanessa Automation

План MCP-инструментов для ИИ-ассистента, помогающего писать и анализировать BDD-тесты в Vanessa Automation.

## Обзор архитектуры

```
AI (VS Code Copilot)  ←→  MCP Server (http1c DLL)  ←→  Vanessa Automation (BSL)
                                                           ├─ Monaco Editor (VanessaTabs)
                                                           ├─ Test Runner
                                                           ├─ Step Library (ТаблицаИзвестныхStepDefinition)
                                                           ├─ TestClient (1С)
                                                           └─ Form Inspector (ИсследовательФормы)
```

---

## Принципы проектирования

1. **Минимум инструментов** — объединяем связанные операции в один инструмент с параметрами
2. **Действия возвращают результат** — каждое действие (запуск, шаг) возвращает статус, время, ошибку
3. **Учёт языка** — все инструменты работы с шагами/фичами учитывают `ЯзыкФичи` (ru/en/vi/de/pl/ro/it/lv)
4. **Только полезное для AI** — никаких дымовых тестов, выгрузки, скриншотов

## 1. `getEditorState` — Полное состояние редактора

**Описание:** Возвращает всё о текущем состоянии Monaco-редактора: открытые вкладки, содержимое активного документа, ошибки. Один вызов вместо трёх.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `includeContent` | boolean | Нет | Включить полный текст активного документа (по умолчанию `true`) |

**Возвращает:**

```json
{
  "tabs": [
    {
      "index": 0,
      "title": "Создание контрагента.feature",
      "filename": "C:\\Tests\\features\\agent.feature",
      "modified": false,
      "isActive": true,
      "lineCount": 45
    }
  ],
  "activeDocument": {
    "title": "Создание контрагента.feature",
    "filename": "C:\\Tests\\features\\agent.feature",
    "modified": false,
    "language": "ru",
    "cursorLine": 12,
    "cursorColumn": 5,
    "content": "# language: ru\n@agent\nФункционал: ..."
  },
  "errors": [
    {
      "line": 15,
      "shortMessage": "Неизвестный шаг",
      "fullMessage": "Шаг 'И я нажимаю кнопку \"Ок\"' не найден в библиотеке"
    }
  ],
  "errorCount": 1
}
```

**Источник BSL:** `VanessaTabs.tabStack`, `editor.getContent()`, `editor.getPosition()`, `ДанныеОшибокVanessaEditor`, `ШагиСОшибкамиVanessaEditor`

**Аннотации:** `readOnlyHint`, `idempotentHint`

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| — | — | — | Параметров нет |

**Возвращает:**

```json
{
  "isRunning": false,
  "featureDirectory": "C:\\Tests\\features",
  "currentFeature": {
    "name": "Создание контрагента",
    "fullPath": "C:\\Tests\\features\\agent.feature",
    "language": "ru",
    "tags": ["@smoke", "@agent"]
  },
  "currentScenario": {
    "name": "Создание юр. лица",
    "id": "15",
    "status": "Failed",
    "tags": ["@critical"],
    "retryNumber": 0
  },
  "currentStep": {
    "name": "И я нажимаю кнопку \"Записать\"",
    "lineNumber": 23,
    "status": "Failed",
    "errorMessage": "Кнопка \"Записать\" не найдена",
    "isContextStep": false
  }
}
```

**Источник BSL:** `ПолучитьСостояниеVanessaAutomation()`, `Объект.ИдетВыполнениеСценариев`, `Объект.КаталогФич`, `ЯзыкФичи`

**Аннотации:** `readOnlyHint`, `idempotentHint`

## 3. `searchSteps` — Поиск шагов

**Описание:** Поиск доступных шагов (step definitions) с точным текстовым совпадением без учета регистра и/или фильтрацией по категории. Поддерживает альтернативы через `|`. Учитывает язык текущей фичи для перевода шагов.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `query` | string | Нет | Точный текстовый запрос без учета регистра; можно перечислить альтернативы через `|` (пусто = все шаги) |
| `category` | string | Нет | Фильтр по категории/типу шага (пусто = все категории) |
| `language` | string | Нет | Язык шагов: `"ru"`, `"en"` и др. (по умолчанию — язык текущей фичи) |
| `limit` | number | Нет | Максимум результатов (по умолчанию 50) |

**Возвращает:**

```json
{
  "language": "ru",
  "totalFound": 156,
  "categories": ["Работа с формами.Заполнение", "Работа с формами.Проверки", "..."],
  "steps": [
    {
      "name": "я устанавливаю в поле с именем \"ИмяПоля\" значение \"Значение\"",
      "description": "Устанавливает значение поля формы по программному имени",
      "category": "Работа с формами.Заполнение",
      "snippet": "И я устанавливаю в поле с именем \"${1:ИмяПоля}\" значение \"${2:Значение}\"",
      "sourceFile": "lib/Keywords/FormManagement.epf",
      "parameters": [
        {"name": "ИмяПоля", "position": 1},
        {"name": "Значение", "position": 2}
      ]
    }
  ]
}
```

**Источник BSL:** `ТаблицаИзвестныхStepDefinition` (колонки: `СтрокаДляПоиска`, `СтрокаДляПоискаПеревод`, `СтрокаДляПоискаРусский`, `ТипШага`, `ПредставлениеТеста`, `ОписаниеШага`, `id`, `ИмяФайла`). Фильтрация: `ТаблицаИзвестныхStepDefinition.НайтиСтроки(Новый Структура("ТипШага", category))`, поиск по `СтрокаДляПоиска` / `СтрокаДляПоискаПеревод`.

**Аннотации:** `readOnlyHint`, `idempotentHint`

## 4. `getTestResults` — Результаты прохождения тестов

**Описание:** Подробные результаты выполнения сценария: статус каждого шага, время, ошибки. Если `scenarioId` не указан — возвращает результат текущего/последнего сценария.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `scenarioId` | string | Нет | ID сценария в дереве (если пусто — текущий) |

**Возвращает:**

```json
{
  "scenarioName": "Создание юр. лица",
  "status": "Failed",
  "startTime": "2026-03-18T15:30:00.000Z",
  "endTime": "2026-03-18T15:30:12.456Z",
  "durationMs": 12456,
  "errorMessage": "Кнопка \"Записать\" не найдена на форме",
  "featureFile": "C:\\Tests\\features\\agent.feature",
  "steps": [
    {
      "name": "я открываю форму справочника \"Контрагенты\"",
      "status": "Success",
      "durationMs": 2340,
      "lineNumber": 10,
      "errorMessage": null
    },
    {
      "name": "я нажимаю кнопку \"Записать\"",
      "status": "Failed",
      "durationMs": 105,
      "lineNumber": 23,
      "errorMessage": "Кнопка \"Записать\" не найдена на форме"
    }
  ]
}
```

**Источник BSL:** `ПолучитьРезультатПрохожденияТестовСценария(ИДСтроки)` → структура `{Статус, ВремяНачала, ВремяОкончания, ОписаниеОшибки, РезультатПрохожденияТестовШагов[{Имя, Статус, ВремяНачала, ВремяОкончания, ОписаниеОшибки, НомерСтрокиВФиче}]}`

**Аннотации:** `readOnlyHint`, `idempotentHint`

## 5. `executeStep` — Выполнить произвольный шаг

**Описание:** Выполняет один шаг по тексту. Позволяет ИИ открывать формы, нажимать кнопки, заполнять поля — без необходимости создавать полный сценарий. Возвращает статус и время выполнения.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `stepText` | string | Да | Полный текст шага (`"я открываю форму справочника \"Контрагенты\""`) |

**Возвращает:**

```json
{
  "status": "Success",
  "durationMs": 1250,
  "errorMessage": null
}
```

**Статусы:** `"Success"`, `"Failed"` (ассерт не прошёл), `"Broken"` (ошибка в обработчике), `"Pending"` (шаг не реализован)

**Источник BSL:** Через создание временной строки в дереве + `ВыполнитьШаг()` → `РезультатПрохожденияШага {Статус, ВремяНачала, ВремяОкончания, ОписаниеОшибки}`

**Аннотации:** `destructiveHint` (изменяет состояние тестируемого приложения)

## 6. `runScenario` — Запустить сценарий

**Описание:** Запускает выполнение сценариев в выбранном режиме. Возвращает итоговый результат после завершения.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `mode` | string | Нет | Режим: `"selected"` (по умолчанию), `"all"`, `"reloadAndRun"`, `"fromCurrentStep"` |

**Возвращает:** (после завершения выполнения)

```json
{
  "status": "Failed",
  "totalScenarios": 1,
  "passed": 0,
  "failed": 1,
  "durationMs": 15230,
  "errorMessage": "Кнопка \"Записать\" не найдена"
}
```

**Режимы:**
- `"selected"` → `ВыполнитьВыделенныйСценарий()`
- `"all"` → `КомандаВыполнитьСценарии()`
- `"reloadAndRun"` → `ПерезагрузитьИВыполнитьДанныйСценарий()` — перезагружает .feature с диска перед запуском
- `"fromCurrentStep"` → `ВыполнитьДанныйСценарийСТекущегоШага()`

**Источник BSL:** `ВыполнитьОдинШаг()` / `КомандаВыполнитьСценарии()` и др.

**Аннотации:** `destructiveHint`

## 8. `getFormAnalysis` — Анализ текущей формы

**Описание:** Возвращает полную информацию о текущей форме тестируемого приложения: дерево элементов (имена, типы, значения, видимость, доступность) и текущее состояние как Gherkin-шаги. Объединяет инспектор формы и генератор Gherkin.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `format` | string | Нет | `"full"` (по умолчанию), `"gherkin"` (только Gherkin-шаги), `"elements"` (только дерево) |

**Возвращает:**

```json
{
  "windowTitle": "Контрагент (создание)",
  "formName": "Справочник.Контрагенты.ФормаОбъекта",
  "elements": [
    {
      "name": "Наименование",
      "type": "InputField",
      "title": "Наименование",
      "value": "ООО Ромашка",
      "visible": true,
      "enabled": true,
      "readOnly": false,
      "children": []
    },
    {
      "name": "ГруппаРеквизиты",
      "type": "Group",
      "title": "Реквизиты",
      "visible": true,
      "children": [
        {
          "name": "ИНН",
          "type": "InputField",
          "title": "ИНН",
          "value": "",
          "visible": true,
          "enabled": true
        }
      ]
    }
  ],
  "gherkinSteps": "И элемент формы с именем \"Наименование\" стал равен \"ООО Ромашка\"\nИ элемент формы с именем \"ИНН\" стал равен \"\""
}
```

**Источник BSL:**
- Дерево: `ИсследовательФормы.ЗаполнитьДанныеФормыРекурсивно()` → `{Имя, ТипСтрока, ВидСтрока, Синоним, ТекущаяВидимость, ТекущаяДоступность, ТекущееТолькоПросмотр, Строки[]}`
- Gherkin: `ПолучитьСостояниеТекущегоЭлементаФормы()` / `ПолучитьИзмененияФормыGherkin()`
- Форма: `ПолучитьТекущуюФормуTestClient()` → `ТестируемаяФорма.ИмяФормы`, `.ТекстЗаголовка`

**Аннотации:** `readOnlyHint`

## 10. `manageVariables` — Управление переменными контекста

**Описание:** Чтение, установка и удаление переменных тестового контекста. Один инструмент для всех операций.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `action` | string | Нет | `"get"` (по умолчанию), `"set"`, `"delete"` |
| `name` | string | Нет* | Имя переменной (* обязательно для `set` и `delete`) |
| `value` | string | Нет* | Значение (* обязательно для `set`) |

**Возвращает:**

Для `"get"` без `name`:
```json
{
  "variables": {
    "ТекущийКонтрагент": "ООО Ромашка",
    "НомерДокумента": "00001",
    "ДатаТеста": "18.03.2026"
  }
}
```

Для `"set"` / `"delete"`:
```json
{
  "success": true,
  "name": "ТекущийКонтрагент",
  "action": "set"
}
```

**Источник BSL:** `ЗначенияПеременных()`, `ЗначениеПеременной(Имя)`, `ЗапомнитьЗначение(Имя, Значение)`, `УдалитьПеременную(Имя)`

**Аннотации:** `idempotentHint` (для get/set), `destructiveHint` (для delete)

## 15. `manageBreakpoints` — Управление точками останова

**Описание:** Установка, снятие и просмотр брейкпоинтов в Gherkin-сценариях. Брейкпоинты работают совместно с пошаговой отладкой (`runScenario` + `executeStep`).

| Параметр | Тип | Обязательный | Описание |
|----------|-----|:---:|----------|
| `action` | string | Нет | `"toggle"` (по умолчанию), `"removeAll"`, `"list"` |
| `line` | number | Нет | Номер строки для toggle (если пусто — текущая строка курсора) |
| `filePath` | string | Нет | Путь к файлу (если пусто — текущий документ) |

**Возвращает:**

Для `"toggle"`:
```json
{
  "action": "toggle",
  "line": 15,
  "filePath": "C:\\Tests\\features\\agent.feature",
  "isSet": true
}
```

Для `"removeAll"`:
```json
{
  "action": "removeAll",
  "removedCount": 3
}
```

Для `"list"`:
```json
{
  "breakpoints": [
    {"line": 15, "filePath": "C:\\Tests\\features\\agent.feature"},
    {"line": 23, "filePath": "C:\\Tests\\features\\agent.feature"}
  ]
}
```

**Источник BSL:**
- Toggle: `ПолучитьVanessaEditor().toggleBreakpoint(line)`, `ДобавитьБрейкПоинт(ПолныйПуть)` / `УдалитьБрейкПоинт(ПолныйПуть)`
- Remove all: `БрейкпоинтУбратьВсе()` / `VanessaEditorRemoveBreakPoints()`
- List: `Брейкпоинты` (массив), `БрейкпоинтыVanessaEditor`

**Аннотации:** `idempotentHint`

# Deep analysis of a Vanessa Automation MCP toolset for AI-driven BDD testing

**The 15-tool MCP server for Vanessa Automation is a strong conceptual foundation but has five critical gaps and a broken phase ordering that would prevent an AI agent from completing its most important workflow — autonomously writing and saving .feature files.** The toolset covers runtime inspection and execution well, yet omits file I/O, test suite navigation, and test data management — capabilities that every production AI testing agent requires. Fixing these gaps and reordering the implementation phases would transform this from a "copilot that watches" into an agent that genuinely drives QA automation inside 1C:Enterprise.

This analysis draws on the Anthropic MCP specification (2025-06-18), reference MCP server implementations (Filesystem, Playwright MCP), production AI testing platforms (mabl, BlinqIO, TestSprite), BDD community best practices (Cucumber.io, SpecFlow), and the Vanessa Automation codebase itself (Pr-Mex/vanessa-automation, 603+ stars).

---

## 1. Critical gaps the toolset must address

The most damaging omission is **file I/O**. The current design has no tool to read a .feature file from disk or write one back. The agent can only see what's open in the Monaco editor via `getEditorState`. Production AI testing agents — from Dagger's self-healing pipeline to the OpenObserve "Council of Sub-Agents" system — universally require `ReadFile`, `WriteFile`, and `ListFiles` as foundational tools. The Anthropic reference Filesystem MCP server dedicates **17 tools** to file operations precisely because autonomous agents cannot function without them. Without file I/O, the agent cannot create new .feature files, cannot browse existing test suites, and cannot persist its work.

The second critical gap is **test suite navigation**. There is no tool to list all scenarios in the test tree with their tags, execution status, and file paths. This capability is essential for three workflows: gap analysis ("which business processes lack test coverage?"), selective execution ("run all @smoke scenarios"), and duplicate detection ("does a scenario for this flow already exist?"). The Levi9 AI BDD pipeline explicitly scans existing features before generating new ones to prevent step definition drift — a problem that compounds rapidly without navigation.

**Test data management** is the third gap. Vanessa Automation operates within 1C:Enterprise, where tests interact with catalogs, documents, and registers. Every production AI testing platform — mabl, Functionize, BlinqIO — provides test data capabilities. Without a tool to set up prerequisite data (e.g., creating a test counterparty or document before testing a workflow), the agent cannot write self-contained scenarios. Vanessa Automation already has a "Data Preparation Tool" that generates feature files for test databases; exposing this via MCP would close the gap.

**Step definition source inspection** is the fourth missing capability. When a step fails, the AI agent needs to understand *why* — and that means reading the BSL (1C:Enterprise Script) implementation behind the Gherkin step. The Levi9 approach and OpenObserve's "Analyst" agent both require code-level inspection to diagnose failures accurately. Without it, the agent can only guess from error messages.

**Test isolation and state reset** is the fifth gap. BDD best practices mandate that scenarios run independently and deterministically regardless of execution order. The current toolset provides no mechanism to reset the test environment between runs. In 1C:Enterprise, this typically means clearing transaction data, resetting form states, or reconnecting the test client. LangChain's agent evaluation patterns specifically recommend "clean environment setup" as essential for reproducible testing.

### Summary of critical additions needed

- **`listScenarios`** — List all scenarios in the test tree with tags, status, and file paths
- **`readFeatureFile`** — Read a .feature file from disk by path
- **`writeFeatureFile`** — Write/save a .feature file to disk
- **`getStepSource`** — Retrieve the BSL implementation of a step definition
- **`manageTestData`** — Setup/teardown test data (or invoke data preparation features)

---

## 2. Phase ordering is fundamentally broken

The recommended implementation phases contain a dependency inversion that would block the agent from using Phase 3 tools. **`connectTestClient` is placed in Phase 5, but it is an absolute prerequisite for `executeStep` (Phase 3) and `getFormAnalysis` (Phase 4).** In Vanessa Automation's two-session architecture, the Test Client is a separate 1C:Enterprise session that reproduces user actions. Without connecting it first, no step can execute and no form can be inspected. This is like placing "start the car" after "drive to the store."

Similarly, **`getSettings` is in Phase 5 but provides language context that `searchSteps` (Phase 2) needs**. Vanessa Automation's step definitions are implemented in Russian and mapped to other languages. If the agent doesn't know the current language setting, it will search for steps in the wrong language or generate Gherkin with incorrect keywords.

**`getFormAnalysis` belongs in Phase 3, not Phase 4.** Form inspection is the agent's primary mechanism for understanding what UI elements exist and how to interact with them — it directly feeds test generation. Placing it after execution tools means the agent must write tests blind and only inspect forms during debugging.

### Corrected phase ordering

| Phase | Tools | Rationale |
|-------|-------|-----------|
| **Phase 2 (Read context)** | `getSettings`, `getEditorState`, `getVAState`, `searchSteps`, `checkSyntax` | Settings provides language context all other tools need. Editor and VA state establish baseline. |
| **Phase 3 (Connect + inspect)** | `connectTestClient`, `getFormAnalysis`, `loadFeatures` | Test client connection is a prerequisite for execution. Form analysis feeds test generation. Feature loading populates the test tree. |
| **Phase 4 (Execute + observe)** | `executeStep`, `runScenario`, `stopExecution`, `getTestResults`, `takeScreenshot` | All execution tools grouped together after the test client is connected. |
| **Phase 5 (Debug + refine)** | `manageVariables`, `manageBreakpoints` | Advanced debugging tools used in the fix-and-retry cycle. |

This ordering follows the natural agent workflow: understand context → connect infrastructure → write and execute → debug failures.

---

## 3. Design principles contain a contradiction and miss key MCP guidance

The document states four design principles. **Principle 4 ("only what's useful for AI — no screenshots") directly contradicts tool 14 (`takeScreenshot`).** This isn't necessarily wrong — screenshots *are* useful for AI agents, especially with vision-capable models like GPT-4o and Claude — but the principle statement needs updating. Production platforms universally include screenshot capability: Playwright MCP, Z.AI Vision MCP, mabl, and CoTester all rely on visual capture for failure diagnosis.

**Principle 1 ("minimum tools, combine related operations") partially conflicts with MCP best practices.** The MCP spec favors granular, single-purpose tools. The Anthropic reference Filesystem server has 17 separate tools rather than a single `manageFiles` tool. The Speakeasy analysis of Playwright MCP found that tool clarity matters more than tool count — LLMs handle 15-20 well-described tools better than 5 overloaded ones. The current `manageVariables` (get/set/delete) and `manageBreakpoints` (toggle/list/removeAll) tools suffer from this: **combining read-only and write operations in a single tool makes MCP annotations ambiguous.** If `manageVariables` can both get (read-only) and delete (destructive), what is its `readOnlyHint`? The answer is `false`, which means the agent treats every variable lookup as a potentially destructive operation.

**Principle 2 ("actions return results") aligns perfectly** with MCP best practices. The spec explicitly states that tool execution errors should be returned within the result using `isError: true`, not as protocol-level errors. This lets the LLM see errors and take corrective action.

**Principle 3 ("language awareness") is essential** for Vanessa Automation's bilingual architecture. The step definition mapping between Russian and English is a unique challenge. However, the implementation should follow the Cucumber community guideline: "The language you choose for Gherkin should be the same language your users and domain experts use."

### Annotation corrections

Based on the MCP spec defaults (readOnlyHint=**false**, destructiveHint=**true**, idempotentHint=**false**, openWorldHint=**true**), every tool should have explicit annotations. The correct mappings:

| Tool | readOnlyHint | destructiveHint | idempotentHint | openWorldHint |
|------|:---:|:---:|:---:|:---:|
| getEditorState | ✅ true | — | — | false |
| getVAState | ✅ true | — | — | false |
| searchSteps | ✅ true | — | — | false |
| getTestResults | ✅ true | — | — | false |
| executeStep | false | false | false | false |
| runScenario | false | false | false | false |
| stopExecution | false | false | ✅ true | false |
| getFormAnalysis | ✅ true | — | — | false |
| checkSyntax | ✅ true | — | — | false |
| manageVariables | ⚠️ ambiguous | ⚠️ ambiguous | ⚠️ ambiguous | false |
| connectTestClient | false | false | ✅ true | false |
| loadFeatures | false | false | ✅ true | false |
| getSettings | ✅ true | — | — | false |
| takeScreenshot | ✅ true | — | — | false |
| manageBreakpoints | ⚠️ ambiguous | ⚠️ ambiguous | ⚠️ ambiguous | false |

The ⚠️ entries highlight why `manageVariables` and `manageBreakpoints` should be split into separate read/write tools or at minimum use `readOnlyHint: false` with `destructiveHint: true` (the conservative default).

## 4. Three critical workflow scenarios are missing

The document describes four "typical scenarios," but real-world AI QA agent research reveals at least three additional workflows that production teams regularly need.

**Coverage gap analysis workflow** is the most impactful missing pattern. The OpenObserve "Architect" agent and mabl's semantic coverage analysis both demonstrate this: the agent examines existing test suites, identifies untested business flows, prioritizes gaps by risk, and generates scenarios to fill them. This workflow requires `listScenarios` (missing), `readFeatureFile` (missing), `getFormAnalysis`, and `searchSteps`. Without it, the agent can only write tests when explicitly told what to test — it cannot proactively discover what's missing.

**Test data preparation workflow** addresses a fundamental challenge in enterprise BDD testing. 1C:Enterprise applications require realistic reference data — counterparties, nomenclature, warehouses, price lists — before functional tests can run. The workflow: agent inspects form requirements → identifies prerequisite data → generates data preparation feature files (using Vanessa Automation's built-in data preparation tool) → executes them → then runs the functional test. Vanessa Automation already supports this conceptually; exposing it via MCP tools would be straightforward.

**Test maintenance and self-healing workflow** covers the scenario where existing tests break due to UI changes in the 1C configuration. The canonical self-healing cycle (documented by QA Wolf with six distinct failure types) is: detect failure → analyze root cause (locator change vs. real bug) → update test → re-run → verify fix. The current toolset supports the run-and-check portion but lacks the file-write capability to actually fix the test. Production platforms like mabl report that **self-healing eliminates 80%+ of test maintenance effort**.

### Existing workflow gaps within the four documented scenarios

The "write new feature file" scenario likely assumes the agent writes into the Monaco editor. But in practice, the agent needs to: check if a similar scenario already exists (requires `listScenarios`), inspect the target form (requires `getFormAnalysis`, correctly dependent on `connectTestClient`), search for reusable steps (covered by `searchSteps`), write the file to disk (requires `writeFeatureFile`), and validate it (covered by `checkSyntax`). The dependency chain is broken without file I/O and test suite navigation.

## 5. Nice-to-have additions that would differentiate the toolset

**Allure report reading** would enable the agent to analyze historical test results, detect flaky tests, and identify trends. Vanessa Automation already integrates with Allure natively. Exposing report data via an MCP tool would enable the coverage gap analysis and flakiness detection workflows.

**Scenario Outline / Examples table generation** support would be valuable but is likely handleable through existing tools. The agent can generate Scenario Outline syntax in .feature files using `searchSteps` to find parameterizable steps and `writeFeatureFile` to save the result. No dedicated tool needed, but the `searchSteps` tool description should explicitly mention which steps support parameterization.

**Export script library browsing** would help the agent discover and reuse Vanessa Automation's export scripts — parameterized, reusable scenario fragments. This is analogous to the Levi9 approach of scanning existing features for step reuse. A dedicated tool or an extension to `searchSteps` with a `category: "export_scripts"` filter would suffice.

**Background section awareness** doesn't require a dedicated tool but should be documented in tool descriptions. The agent needs to understand that Background sections run before every scenario in a feature file, which affects both test generation (what can be assumed) and performance (Background steps multiply execution time).

## 6. Things to simplify or split

**Split `manageVariables` into `getVariables` and `setVariable`** (with delete as a variant of set). This resolves the annotation ambiguity and follows the MCP filesystem server pattern where `read_file` and `write_file` are separate tools. The LLM can more accurately select the right tool when intentions are clear from the name.

**Split `manageBreakpoints` into `listBreakpoints`, `toggleBreakpoint`, and `clearBreakpoints`**. Same reasoning — listing is read-only, toggling is idempotent write, clearing is destructive. Each has different annotation profiles.

**Consider merging `getEditorState` and `checkSyntax`** if syntax errors are already part of the editor state. The document mentions `getEditorState` returns "syntax errors" — if so, `checkSyntax` may be redundant. If they serve different purposes (editor state = cursor/tab info, checkSyntax = deep Gherkin validation), keep them separate but clarify the distinction in tool descriptions.

**`runScenario`'s four modes** (selected, all, reloadAndRun, fromCurrentStep) could be simplified. The `reloadAndRun` mode is really `loadFeatures` + `runScenario(all)` — a composite operation. Per MCP design philosophy, composable atomic tools are preferred over multi-mode tools. Consider whether `reloadAndRun` should just be a documented pattern ("call `loadFeatures` then `runScenario`") rather than a mode.

---

## 7. Multi-language support assessment

Vanessa Automation supports Russian and English through a translation mapping architecture where English Gherkin steps map to Russian BSL implementations. The question of whether "8 languages" is enough depends on the user base. **For the 1C:Enterprise ecosystem, Russian and English cover the vast majority of users.** Gherkin itself supports 70+ languages, but Vanessa Automation's step definitions would need translation for each additional language — a significant effort. The current approach is pragmatically correct.

The more important concern is **language handling in the MCP tools**. The `searchSteps` tool must accept a language parameter and return results in the correct language. The `checkSyntax` tool must validate against the correct Gherkin dialect. And critically, `getSettings` must be available early (Phase 2, not Phase 5) so the agent knows which language to use for all subsequent operations. The Cucumber community is emphatic: "Write Gherkin in the language your domain experts use." The agent must respect this, not default to English.

---

## 8. Alignment with industry benchmarks

Comparing this toolset against production AI testing platforms reveals the maturity gap clearly. **mabl's MCP server** provides semantic test search, coverage gap identification, test failure analysis, and Jira integration. **TestSprite's MCP server** claims to boost pass rates from 42% to 93% through its plan→generate→execute→debug→validate cycle. **Playwright MCP** exposes ~20 tools with accessibility tree snapshots for deterministic form inspection.

The Vanessa Automation MCP server is closer to **Phase 1-2 maturity** on a typical AI testing agent maturity curve: it can inspect state and execute tests, but cannot autonomously create, persist, or maintain tests. Adding file I/O, test suite navigation, and a corrected phase ordering would bring it to Phase 3-4 maturity — where autonomous write-run-debug cycles become possible.

The **tool count of 15 is within the sweet spot** (5-20 tools per MCP server based on reference implementations). With the recommended splits (manageVariables → 2, manageBreakpoints → 3) and additions (5 new tools), the total would reach ~22-23 tools. This is at the upper boundary but manageable — Playwright MCP operates well with ~20 tools, and the Filesystem server uses 17. Descriptive tool names and clear descriptions matter more than raw count.
