# Инструкция по тестированию MCP-вызовов для ИИ

Документ описывает, как ИИ должен проверять MCP-вызовы Vanessa Automation после изменения логики инструментов.

## Цель тестирования

Нужно убедиться, что:

- каждый MCP-инструмент вызывается без ошибок
- каждый ресурс возвращает данные по URI
- каждый промпт возвращает системное сообщение
- ответ приходит в ожидаемом формате
- для инструментов с параметрами корректно обрабатываются разные варианты передачи аргументов
- после изменения кода MCP рантайм действительно использует обновленную реализацию

## Общие правила

Перед тестированием:

1. Убедиться, что собрана актуальная версия Vanessa Automation.
2. Убедиться, что MCP-сеанс переподключен после обновления модуля.
3. Если инструмент возвращает старый формат ответа, сначала проверить, не работает ли старая сессия.

Во время тестирования:

1. Проверять не только успешный вызов, но и содержимое ответа.
2. Все числовые значения (количество, время) должны корректно отображаться, включая нулевые — без пустых строк. Используется `Формат(X, "ЧГ=0; ЧН=0")`.
3. При неудаче или пустом результате ответ должен содержать секцию «Следующие шаги» с подсказками, какие инструменты вызвать.
4. Для `connectTestClient` при неудаче — ответ содержит список доступных профилей.
5. Для `searchSteps` обязательно проверять несколько комбинаций параметров.
6. Если инструмент зависит от состояния редактора или формы, сначала зафиксировать текущее состояние через `getVAState`.
7. Если `searchSteps` сначала пустой, повторный вызов допустим: инструмент может запускать штатную загрузку шагов перед ответом.
8. При тестировании `searchSteps` отдельно проверять область поиска `searchScope`.
6. Инструменты, требующие подключённого TestClient (`executeStep`, `executeFeatureStep`, `getFormAnalysis`, `runScenario`, `takeScreenshot`), нужно тестировать после `connectTestClient`.

2. Ответ не пустой.
3. Ответ является текстовой строкой с датой и временем.

Минимальный тест:


Ожидаемый результат:

- строка вида `ДД.ММ.ГГГГ ЧЧ:ММ:СС`

## Фаза 2: Контекст для AI

### 2. `getVAState`

Что проверить:

1. Вызов без параметров.
2. Ответ приходит в Markdown.
3. В ответе есть секции:
   - `Состояние Vanessa Automation`
   - `Текущая фича`
   - `Текущий сценарий`
   - `Текущий шаг`
4. Даже при отсутствии активной фичи ответ должен быть валидным и человекочитаемым.

Минимальный тест:

```json
{}
```

Ожидаемый результат:

- markdown-документ
- нет JSON-строки в поле `text`

### 3. `searchSteps`

Это основной инструмент для параметризованного тестирования.

#### Базовый сценарий

Проверить вызов:

```json
{}
```

Что проверить:

1. Ответ приходит в Markdown.
2. Есть сводка с количеством найденных шагов.
3. Если шаги найдены, выводится список шагов.
4. Если кэш шагов не был загружен заранее, инструмент все равно должен вернуть ответ после своей внутренней загрузки.

#### Проверка параметра `limit`

Проверить вызовы:

```json
{"limit": 1}
```

```json
{"limit": 5}
```

```json
{"limit": 50}
```

Что проверить:

1. Количество реально показанных элементов не превышает `limit`.
2. Общее количество найденных элементов продолжает считаться корректно.

#### Проверка параметра `query`

Проверить несколько вариантов:

```json
{"query": "allure", "limit": 10}
```

```json
{"query": "И я нажимаю на кнопку с именем 'ФормаЗаписать'", "searchScope": "name", "limit": 10}
```

```json
{"query": "несуществующий_поисковый_текст_12345", "limit": 10}
```

Что проверить:

1. Поиск выполняется по подстроке без учета регистра.
2. Для запроса по части текста существующего шага есть непустая выдача.
3. Для несуществующего запроса ответ остается валидным Markdown.
4. При пустой выдаче явно написано, что совпадения не найдены.

#### Проверка альтернатив через `|`

Проверить вызовы:

```json
{"query": "Первая точная фраза|Вторая точная фраза", "limit": 10}
```

```json
{"query": "  Первая точная фраза  |  Вторая точная фраза  ", "limit": 10}
```

```json
{"query": "Несуществующая фраза 1|Несуществующая фраза 2", "limit": 10}
```

Что проверить:

1. Каждая часть `query` вокруг `|` обрезается по краям перед сравнением.
2. Совпадение находится, если подходит хотя бы одна из альтернатив по подстроке.
3. В ответе явно указано, что поиск текстовый, не семантический.
4. При пустой выдаче ответ остается корректным Markdown.

#### Проверка параметра `searchScope`

Проверить вызовы:

```json
{"query": "эпика", "searchScope": "name", "limit": 10}
```

```json
{"query": "Задает", "searchScope": "all", "limit": 10}
```

```json
{"query": "Задает", "searchScope": "name", "limit": 10}
```

Что проверить:

1. `name` ищет только по названию шага.
2. `all` ищет шире и должен находить совпадения по описанию.
3. В ответе явно указано, по какой области выполнялся поиск.

#### Проверка параметра `category`

Проверить вызовы:

```json
{"category": "Прочее.Allure", "limit": 10}
```

```json
{"category": "UI.Формы", "limit": 10}
```

```json
{"category": "НесуществующаяКатегория", "limit": 10}
```

Что проверить:

1. Для существующих категорий выводятся только релевантные шаги.
2. Для несуществующей категории ответ корректен и не падает.

#### Комбинированные проверки параметров

Проверить вызовы:

```json
{"query": "эпика", "category": "Прочее.Allure", "limit": 5}
```

```json
{"query": "И я нажимаю на кнопку с именем 'ФормаЗаписать'|И я нажимаю кнопку 'Записать'", "category": "Работа с формами.Команды", "searchScope": "name", "limit": 5}
```

```json
{"query": "таблица", "category": "UI.Таблицы", "searchScope": "all", "limit": 3}
```

```json
{"query": "форма", "category": "НесуществующаяКатегория", "searchScope": "name", "limit": 3}
```

Что проверить:

1. Одновременная фильтрация по `query` и `category` работает предсказуемо.
2. Одновременная фильтрация по `query` с альтернативами через `|` и `category` работает предсказуемо.
3. Ограничение `limit` продолжает соблюдаться.
4. Пустой результат не считается ошибкой.

#### Проверка некорректного `limit`

Проверить вызовы:

```json
{"limit": "abc"}
```

```json
{"searchScope": "invalid"}
```

```json
{"limit": -1}
```

```json
{"limit": 0}
```

Что проверить:

1. Для некорректного `searchScope` и отрицательного `limit` сервер возвращает понятную ошибку.
2. При `limit = 0` инструмент возвращает все результаты.
3. Если значение не проходит schema-валидацию на уровне инструмента, это тоже считается корректным защитным поведением.

### 4. `checkSyntax`

Что проверить:

1. Вызов без параметров.
2. Ответ приходит в Markdown.
3. При отсутствии ошибок возвращается:
   - признак корректности
   - количество проблем `0`
4. При наличии ошибок должен выводиться список проблем с номерами строк.

Минимальный тест:

```json
{}
```

Расширенный тест:

1. Открыть заведомо корректный `.feature` файл.
2. Выполнить `checkSyntax`.
3. Открыть `.feature` файл с ошибкой или временно внести синтаксическую ошибку.
4. Повторить `checkSyntax`.
5. Убедиться, что ответ меняется ожидаемым образом.

### 5. `getEditorState`

Что проверить:

1. Вызов без параметров — возвращает содержимое.
2. Вызов с `{"includeContent": false}` — содержимое не включается.
3. Ответ содержит секции:
   - список вкладок
   - активный документ
   - позиция курсора
   - ошибки
4. При отсутствии открытых вкладок ответ остаётся валидным.

Минимальный тест:

```json
{}
```

Расширенный тест:

1. Открыть файл `.feature` в редакторе VA.
2. Вызвать `getEditorState`.
3. Убедиться, что вкладка видна в ответе, содержимое соответствует файлу.
4. Вызвать `{"includeContent": false}` — убедиться, что content отсутствует.

Ожидаемый результат:

- Markdown с секциями `Open Tabs`, `Active Document`, `Content`, `Errors`
- количество вкладок и содержимое соответствуют реальному состоянию

## Фаза 3: Подключение и инспекция

### 6. `connectTestClient`

Что проверить:

1. Вызов с валидным именем профиля подключает TestClient.
2. Вызов с несуществующим профилем возвращает понятную ошибку.
3. После успешного подключения `getVAState` отражает подключённый клиент.

Минимальный тест:

```json
{"profileName": "ИмяПрофиляИзVA"}
```

Ожидаемый результат:

- Markdown с подтверждением подключения
- или понятное сообщение об ошибке

Предусловие: в настройках VA должен быть настроен хотя бы один профиль подключения.

### 7. `getFormAnalysis`

Предусловие: TestClient подключён, открыта какая-либо форма.

Что проверить:

1. Вызов без параметров (формат `"full"`) — возвращает и элементы и Gherkin.
2. Вызов с `{"format": "gherkin"}` — только Gherkin-шаги.
3. Вызов с `{"format": "elements"}` — только дерево элементов.
4. Если TestClient не подключён, возвращается понятная ошибка.
5. Gherkin-шаги соответствуют реальному состоянию формы.

Минимальный тест:

```json
{}
```

Расширенный тест:

1. Подключить TestClient.
2. Выполнить шаг: открыть форму справочника.
3. Вызвать `getFormAnalysis` — проверить, что элементы формы присутствуют.
4. Вызвать `{"format": "gherkin"}` — проверить, что Gherkin-шаги валидны.

### 8. `loadFeatures`

Что проверить:

1. Вызов без параметров — перезагружает текущий каталог фич.
2. Вызов с `{"path": "..."}` — устанавливает новый каталог и загружает.
3. Вызов с несуществующим путём — возвращает ошибку.

Минимальный тест:

```json
{}
```

Ожидаемый результат:

- Markdown с подтверждением загрузки
- каталог фич соответствует ожиданию

## Фаза 4: Выполнение и наблюдение

### 9. `executeStep`

Предусловие: TestClient подключён.

Что проверить:

1. Вызов без `stepText` возвращает понятную ошибку валидации.
2. Вызов с `stepText` выполняет именно переданный шаг, а не текущий выделенный шаг.
3. Ответ содержит статус (Success/Failed/Broken/Pending) и не подхватывает старый результат от предыдущего запуска.
4. При ошибке выводится текст ошибки.
5. Если TestClient не подключён — понятная ошибка.

Минимальный тест:

```json
{"stepText": "И я закрыл все окна клиентского приложения"}
```

Расширенный тест:

1. Подключить TestClient.
2. Вызвать `executeStep` с конкретным `stepText`.
3. Проверить, что выполнился именно переданный шаг и статус `Success`.
4. Сразу после этого вызвать другой `stepText` и убедиться, что ответ не содержит шаг или статус от предыдущего вызова.

### 10. `runScenario`

Предусловие: TestClient подключён, загружена фича с хотя бы одним сценарием.

Что проверить:

1. Вызов без параметров (`mode: "all"`) — выполняет все загруженные сценарии.
2. Вызов с `{"filePath": "..."}` — загружает .feature, открывает её в редакторе и запускает.
3. Вызов с `{"mode": "reloadAndRun"}` — перезагружает и выполняет выбранный сценарий.
4. Вызов с `{"mode": "selected"}` — выполняет выделенный сценарий.
5. Ответ содержит итоговый статус, количество пройденных/упавших.
6. Прогресс отправляется через SendProgress (если поддерживается клиентом).

Минимальный тест:

```json
{}
```

```json
{"filePath": "C:\\Tests\\features\\smoke.feature"}
```

```json
{"mode": "reloadAndRun"}
```

Расширенный тест:

1. Загрузить фичу с 3+ шагами.
2. Запустить `{"mode": "selected"}`.
3. Убедиться, что ответ приходит после завершения (не сразу).
4. В ответе есть результаты по шагам.

### 11. `stopExecution`

Что проверить:

1. Вызов при выполняющемся сценарии останавливает выполнение.
2. Вызов без запущенных сценариев не вызывает ошибку (idempotent).
3. Ответ содержит информацию о том, было ли остановлено выполнение.

Минимальный тест:

```json
{}
```

Расширенный тест:

1. Запустить длинный сценарий через `runScenario`.
2. Вызвать `stopExecution`.
3. Убедиться, что выполнение остановлено.

### 12. `getTestResults`

Что проверить:

1. Вызов без параметров возвращает результат последнего сценария.
2. Вызов с `{"scenarioId": "..."}` — результат конкретного сценария.
3. Ответ содержит таблицу шагов со статусами и временем.
4. Если ничего не запускалось — возвращается информативное сообщение.

Минимальный тест (после запуска сценария):

```json
{}
```

```json
{"scenarioId": "15"}
```

Ожидаемый результат:

- Markdown с секциями: заголовок, общая информация, таблица шагов
- статусы шагов: ✅ / ❌

### 13. `takeScreenshot`

Предусловие для успешного сценария: TestClient подключён, запущен и открыта форма.

Что проверить:

1. При отсутствии запущенного TestClient вызов без параметров возвращает ошибку с подсказкой сначала вызвать `connectTestClient`.
2. После `connectTestClient` вызов без параметров делает скриншот клиента тестирования.
3. Вызов через сам MCP tool и прямой вызов через `curl` оба завершаются успешно.
4. Ответ содержит Markdown-подтверждение и встроенное изображение, а не путь к временному файлу.
5. Base64 изображения не содержит переводов строк; вызов через tool не должен падать с ошибкой `Unexpected base64 character`.
6. Инструмент всегда делает снимок только клиента тестирования и не должен делать снимок всего экрана.
7. Если VanessaExt не загружен — возвращает понятную ошибку с подсказкой проверить настройки раздела «Скриншоты».
8. Если клиент тестирования заблокирован модальным окном — возвращает понятную ошибку с предложением закрыть модальное окно и повторить `takeScreenshot`.

Минимальный тест:

```json
{}
```

## Фаза 5: Отладка и вспомогательные

### 14. `manageVariables`

Что проверить:

1. `{"action": "get"}` — возвращает все переменные.

5. `{"action": "delete", "name": "Тест"}` — удаляет переменную.
6. Повторный get после delete — переменная отсутствует.

```json
{}
```

```json
{"action": "set", "name": "MCPТестовая", "value": "Привет"}
```

```json
{"action": "get", "name": "MCPТестовая"}
```

```json
{"action": "delete", "name": "MCPТестовая"}
```

```json
{"action": "get", "name": "MCPТестовая"}
```

### 15. `manageBreakpoints`

Предусловие: открыт файл `.feature` в редакторе VA.

Что проверить:

3. Повторный `{"action": "list"}` — отражает изменение.

Минимальный тест:


Расширенный тест:

```json
{"action": "toggle", "line": 5}
```

```json
{"action": "list"}
```

```json
{"action": "removeAll"}
```

```json
{"action": "list"}
```

## Тестирование ресурсов

### R1. `va://state`

Что проверить:

1. Ресурс возвращает Markdown с состоянием VA.
2. Содержимое аналогично ответу `getVAState`, но через resource protocol.
3. MIME type — `text/markdown`.

### R2. `va://variables`

Что проверить:

1. Ресурс возвращает Markdown-таблицу переменных.
2. Если переменных нет, таблица пустая или с соответствующим сообщением.
3. После `manageVariables` с action "set", повторное чтение ресурса отражает новую переменную.

---

## Тестирование промптов

### P1. `quickStart`

Что проверить:

1. Вызов без параметров возвращает системное сообщение.
2. Сообщение содержит инструкции по архитектуре MCP, порядку работы и типовым сценариям.
3. Вызов с `{"task": "Проверить форму списка"}` тоже работает и дополняет инструкцию рекомендациями для задачи.

---

## Признаки успешной проверки

Можно считать, что MCP-инструменты проверены успешно, если:

1. Все 17 инструментов вызываются без аварийного завершения.
2. Оба ресурса (`va://state`, `va://variables`) возвращают данные.
3. Промпт `quickStart` возвращает системное сообщение.
4. `getVAState`, `searchSteps`, `checkSyntax`, `getEditorState` возвращают Markdown, а не JSON-строку.
5. `searchSteps` возвращает непустой список шагов хотя бы на одном тестовом запросе.
6. `manageVariables` проходит полный цикл: set → get → delete → get.
7. `connectTestClient` → `getFormAnalysis` работает при наличии тестируемого приложения.
8. Проверены как минимум:
   - вызов без параметров
   - вызов с валидными параметрами
   - вызов с пустой выдачей
   - вызов с некорректным значением `limit`
   - вызов с разными значениями `searchScope`

## Если проверка не прошла
