# MCP в Vanessa Automation

## Быстрый старт

Для начала использования MCP в Vanessa Automation выполните следующие шаги:

1. **Настройте LLM с поддержкой MCP**. У вас должна быть работающая LLM, к которой можно подключить MCP инструменты. Например, VSCode + плагин Cline — это среда, где вы пишете промты.

2. **Установите расширение client_mcp в базу менеджера тестирования**. В базу менеджера тестирования необходимо поставить расширение из [проекта](https://github.com/1c-neurofish/onec-client-mcp-devkit/releases). В базе расширение должно быть установлено под именем `client_mcp` и активно — по этому имени Vanessa Automation находит его при старте.

3. **Запустите сеанс 1С как менеджер тестирования и откройте в нём Vanessa Automation**. Сеанс обязательно должен быть запущен с ключом `/TestManager` — только такой сеанс является менеджером тестирования; на работу в этом режиме рассчитаны MCP-инструменты управления клиентом тестирования. Что и где именно запускать — в разделе [Запуск MCP сервера: что и где запускать](#запуск-mcp-сервера-что-и-где-запускать). При старте Vanessa Automation зарегистрирует свои инструменты MCP (если расширение `client_mcp` найдено).

4. **MCP сервер запустится сам**. Если Vanessa Automation найдёт в базе расширение `client_mcp`, она сама запустит сервер MCP — отдельно запускать его не нужно. Условия автозапуска, порт и ручной запуск описаны в разделе [Запуск MCP сервера: что и где запускать](#запуск-mcp-сервера-что-и-где-запускать).

5. **Настройте MCP клиент в вашей IDE**. В вашей IDE, где работает LLM, необходимо прописать настройки MCP сервера, который запущен в менеджере тестирования. В инструкции ниже приведены примеры настроек для плагина Continue (для VSCode), плагина Cline и плагина Roo Code (тоже для VSCode).

6. **Включите внешнюю компоненту VanessaExt**. В Vanessa Automation необходимо включить использование внешней компоненты VanessaExt.

7. **Установите расширение VAExtension**. В базу клиента тестирования необходимо добавить расширение VAExtension.

8. **Настройка завершена**. После выполнения всех шагов MCP готов к работе.

## Запуск MCP сервера: что и где запускать

Сервер MCP — это не отдельная программа. Он поднимается внутри сеанса 1С:Предприятие, в котором открыта Vanessa Automation, поэтому скачивать или устанавливать его отдельно не нужно.

### Где запускать

Всё запускается на том компьютере, где должен работать менеджер тестирования — как правило, это тот же компьютер, на котором установлена ваша IDE с LLM. Сеанс 1С:Предприятие с открытой Vanessa Automation становится менеджером тестирования, а сервер MCP принимает подключения от вашей IDE.

### Что запускать: сеанс 1С в режиме менеджера тестирования

Запускается обычный сеанс 1С:Предприятие, но обязательно с ключом `/TestManager` — только сеанс с этим ключом является менеджером тестирования. Если запустить Vanessa Automation в обычном сеансе (без ключа), менеджером тестирования он не станет: сервер MCP в нём может подняться, но MCP-инструменты управления клиентом тестирования рассчитаны на сеанс менеджера тестирования.

Пример запуска из командной строки:

```batch
"C:\Program Files\1cv8\8.3.27.2130\bin\1cv8c.exe" ENTERPRISE /IBConnectionString "File=""c:\Bases\8.3.27"";" /TestManager /Execute "C:\Commons\rep\vanessa-automation\vanessa-automation.epf"

```

* `1cv8c.exe` — тонкий клиент (исполняемый файл толстого клиента — `1cv8.exe`). Путь к исполняемому файлу подставьте от своей версии платформы.
* `/IBConnectionString` — строка соединения с базой менеджера тестирования (в примере — файловая база `c:\Bases\8.3.27`).
* `/TestManager` — ключ запуска сеанса в режиме менеджера тестирования (в проекте встречается и написание `/TESTMANAGER`).
* `/Execute` — путь к файлу `vanessa-automation.epf`.

Эту же команду можно сохранить в ярлык или bat-файл, подставив свои пути. Для отладки сеанс можно запускать из конфигуратора, добавив `/TestManager` в дополнительные параметры запуска.

Если Vanessa Automation уже открыта в обычном сеансе, её можно перезапустить как менеджер тестирования — командой **Перезапустить как менеджер тестирования** в командной панели окна Vanessa Automation (дополнительное подменю). Команда видна, только пока сеанс не является менеджером тестирования.

### Автозапуск сервера MCP

Отдельно запускать сервер MCP не нужно: **если Vanessa Automation находит в базе расширение `client_mcp`, она запускает сервер MCP сама** — при старте, после регистрации инструментов MCP.

Автозапуск работает, когда выполнены все условия:

* в базе, где запущен сеанс, установлено и активно расширение `client_mcp`;
* на закладке **AI** настроек Vanessa Automation включена настройка «Запускать сервер MCP при запуске VA» (включена по умолчанию);
* Vanessa Automation не запущена в режиме самотестирования.

Сервер поднимается на порту из настройки «Порт сервера MCP» на той же закладке **AI** (по умолчанию 9874; если порт не задан или задан неверно, используется 9874). Обе настройки можно задать и параметрами StartMCPServerOnVAStartup и MCPServerPort, например в файле VAParams.json.

Если сервер уже запущен (например, его запустили вручную), автозапуск ничего не делает и настройка «Порт сервера MCP» не применяется.

Автозапуск не действует, если свой MCP-транспорт установил внешний плагин (внешний фасад расширения) — в этом случае транспортом управляет плагин.

### Ручной запуск сервера MCP

Если автозапуск отключён или сервер нужно запустить вручную:

* запустите сервер из формы управления MCP расширения `client_mcp` (кнопка запуска сервера);
* либо попросите расширение запустить сервер сразу при старте сеанса, передав в командной строке:

```batch
"C:\Program Files\1cv8\8.3.27.2130\bin\1cv8c.exe" ENTERPRISE /IBConnectionString "File=""c:\Bases\8.3.27"";" /TestManager /Execute "C:\Commons\rep\vanessa-automation\vanessa-automation.epf" /C "runMcp;mcpPort=9874"

```

В параметре `mcpPort` можно указать свой порт сервера, но он должен совпадать с портом в настройках MCP-клиента (в примерах конфигов ниже — 9874).

### Диагностика MCP в журнале регистрации

Если нужно разобрать работу MCP (загрузку фич, запуск сценариев, проверку синтаксиса), включите на закладке **AI** настройку «Записывать служебные данные MCP в журнал регистрации» (параметр `AIЗаписыватьСлужебныеДанныеВЖР` / `WriteMCPServiceDataToEventLog`). По умолчанию настройка выключена.

События пишутся в журнал регистрации базы, где запущена Vanessa Automation, с префиксом `VanessaAutomation.MCP.` и уровнем «Информация». В данных события передаются только служебные поля: режим, идентификатор вызова, путь к файлу, номера строк, статусы и признаки. Тексты ошибок и значения полей тестируемого приложения в события MCP не записываются. Записи удобно отбирать по префиксу события `VanessaAutomation.MCP.` (в инструменте `get_event_log_manager` — `event_match_type: starts_with`).

При включённой настройке вызовы инструментов Vanessa Automation, у которых не было события начала, пишутся событием `VanessaAutomation.MCP.Инструмент.Запрос`: имя инструмента, идентификатор вызова и имена параметров. Значения параметров не записываются. У инструментов `check_syntax`, `open_feature_file`, `load_features`, `execute_feature_step`, `run_scenario`, `stop_scenario` и `restart_vanessa` остаются их прежние события начала (`СинтаксКонтроль.Запрос`, `ОткрытиеФичаФайла.Запрос`, `Шаг.Запрос`, `Сценарий.Запрос`, `Сценарий.Остановка`, `Перезапуск.Вызов`, `Перезапуск.Запрос`). В ветках отказа `run_scenario`, `open_feature_file` и `load_features`, которые завершаются до своего события начала, запись о вызове может отсутствовать. Инструменты, зарегистрированные расширением (например, `infobase_info`), этим событием не покрываются.

При частом опросе `get_vanessa_automation_state` и `get_test_results` журнал растёт, а каждая запись выполняется серверным вызовом и может добавлять задержку: включайте настройку на короткое время диагностики. Вызов самого `get_event_log_manager` тоже пишется в журнал и может попасть в читаемую выборку.

### Проверка

Запущенный сервер MCP отвечает по адресу `http://<компьютер менеджера тестирования>:<порт>/mcp`. Если IDE работает на том же компьютере, в настройках MCP клиента указывается `http://localhost:9874/mcp` — примеры конфигов для разных плагинов приведены ниже. Через MCP доступно управление сеансом 1С, поэтому не открывайте порт сервера во внешнюю сеть — для удалённого подключения используйте доверенную сеть.


## 🚀 Реальный проект покрытия тестами

Файлы из `examples/МультиАгент/` — это **шаблоны**. Для покрытия тестами конкретной конфигурации 1С создаётся **реальный проект** — отдельный каталог, в котором лежат копии шаблонов и проектные данные.

### 📂 Структура реального проекта

```
<корень_проекта>/
├── ТестПлан.MD                  ← Вход: тесты в свободной форме (Дано/Когда/Тогда)
├── ТестПлан.pdf                 ← PDF-версия для согласования (опционально)
├── ПараметрыКонфигурации.MD     ← Пути к DT, исходникам, профилю (ОБЯЗАТЕЛЬНО)
│
├── InstructionsResearch.md       ← Копия шаблона
├── InstructionsWriteScenario.md ← Копия шаблона
├── ПодготовкаУправляющегоАгента.MD ← Копия шаблона
│
├── ПромптыСубагентов/           ← Копии промптов субагентов
│
├── Чеклисты/                    ← Чек-листы для ревьюеров
│   └── *.MD
│
├── dt/                          ← DT-эталон и лог restore
│   ├── <Эталон>.dt
│   └── log.txt
│
├── data/                        ← Выход: анализ командного интерфейса
│   └── АнализДанных_<NN>_<...>.MD
│
├── research/                    ← Выход: результаты исследования
│   └── РезультатИсследования_<NN>_<...>.MD
│
├── features/                    ← Выход: готовые feature-файлы
│   └── <NN>_<КраткоеНазвание>.feature
│
├── rewiew/                      ← Выход: отчёты ревьюеров
│   ├── rewiew_<NN>_<...>_Researcher_<N>.MD
│   └── rewiew_<NN>_<...>_Writer_<N>.MD
│
├── restore/                     ← Выход: отчёты о восстановлении базы
│   └── Restore_<NN>_<...>.MD
│
├── writer/                      ← Выход: логи работы Писателя
│   └── ПисательСценариев_<NN>_<...>.MD
│
├── png/                         ← Скриншоты (создаются при отладке)
│
└── Архив/                       ← Старые/неактуальные файлы
```

### 🔄 Полный workflow от ТестПлан.MD до готовых feature-файлов

```
ВХОДЫ (пользователь):
├── ТестПлан.MD           — тесты в свободной форме
├── dt/<Эталон>.dt        — эталонное состояние базы
└── ПараметрыКонфигурации.MD — пути проекта

         ↓

УПРАВЛЯЮЩИЙ АГЕНТ (оркестратор):
1. Парсит ТестПлан.MD → СПИСОК_СЦЕНАРИЕВ
2. Для каждого сценария запускает цепочку субагентов

         ↓

ВЫХОДЫ (по каждому сценарию):
├── data/АнализДанных_<NN>.MD            ← от АнализДанныхИИнтерфейса
├── research/РезультатИсследования_<NN>.MD ← от Исследователя
├── rewiew/rewiew_<NN>_Researcher.md     ← от Код-Ревьюера (Researcher)
├── features/<NN>_<...>.feature         ← от Писателя
├── rewiew/rewiew_<NN>_Writer.md         ← от Код-Ревьюера (Writer)
├── restore/Restore_<NN>.MD             ← от АдминистраторБазы
└── writer/ПисательСценариев_<NN>.MD    ← лог работы Писателя

         ↓

НАКОПЛЕНИЕ ЗНАНИЙ:
└── Memory.MD  ← по итогам работы сюда записываются
                  новые знания о конфигурации
```

### 📋 Шаги для запуска нового тестового проекта

1. **Создать каталог проекта** (например, `C:\Commons\rep\AI\testERP7\`).
2. **Скопировать шаблоны** из `examples/МультиАгент/`:
   - `InstructionsResearch.md`
   - `InstructionsWriteScenario.md`
   - `ПодготовкаУправляющегоАгента.MD`
   - `ПромптыСубагентов/` (целиком)
   - `Чеклисты/` (целиком)
3. **Создать `ПараметрыКонфигурации.MD`** и заполнить пути.
4. **Подготовить DT-эталон** — положить в `dt/<Эталон>.dt`.
5. **Написать `ТестПлан.MD`** — заполнить тесты в свободной форме.
6. **Запустить Управляющего Агента** (см. `ПодготовкаУправляющегоАгента.MD`).

### 🔗 Связь между шаблонами и реальным проектом

| Шаблон (`examples/МультиАгент/`) | Копия в реальном проекте | Отличия |
|----------------------------------|--------------------------|---------|
| `ПодготовкаУправляющегоАгента.MD` | копируется | обычно без изменений |
| `InstructionsResearch.md` | копируется | может дополняться под конфигурацию |
| `InstructionsWriteScenario.md` | копируется | обычно без изменений |
| `ПромптыСубагентов/*.MD` | копируются в `ПромптыСубагентов/` | обычно без изменений |
| `ПараметрыКонфигурации.MD` (шаблон) | **создаётся** в проекте | заполняется конкретными путями |
| `ТестПлан.MD` (шаблон) | **создаётся** в проекте | заполняется тестами |
| — | `dt/`, `data/`, `features/` и т.п. | создаются автоматически |

### ⚠️ Что НЕ нужно менять

- Шаблоны промптов **уже универсальны** — они читают `ПараметрыКонфигурации.MD` и `ТестПлан.MD` из текущего каталога проекта.
- `ПодготовкаУправляющегоАгента.MD` универсален — он парсит `ТестПлан.MD` и запускает субагентов.
- `Memory.MD` пуст при старте и наполняется по ходу работы.

```yaml
name: VanessaAutomation

mcpServers:

    type: streamable-http
    url: http://localhost:9874/mcp
```

## 🤖 Многоагентный режим покрытия тестами

Для сложных задач используется **многоагентная система**, описанная в
[`examples/МультиАгент/ПодготовкаУправляющегоАгента.MD`](examples/МультиАгент/ПодготовкаУправляющегоАгента.MD).

### Цепочка субагентов для каждого сценария

```
[Пользователь] → ТестПлан.MD
        ↓
Управляющий Агент (парсит ТестПлан, итерирует по сценариям)
        ↓
1. АнализДанныхИИнтерфейса → data/АнализДанных_<NN>.MD
        ↓
2. Исследователь → research/РезультатИсследования_<NN>.MD
        ↓
3. Код-Ревьюер (Researcher) → rewiew/rewiew_<NN>_Researcher.md
        ↓ (если ✅)
4. Писатель → features/<NN>_<...>.feature
        ↓
5. Код-Ревьюер (Writer) → rewiew/rewiew_<NN>_Writer.md
        ↓ (если ✅)
6. ✅ Готово!
        ↓ (следующий сценарий)
7. АдминистраторБазы → restore/Restore_<NN>.MD
```

## 🔗 Рекомендуемый порядок работы с файлами

### Для простого случая (1-2 сценария)

```
ТестПлан.MD (ввод теста в свободной форме)
        ↓
InstructionsResearch.md →  Исследование через UI клиента тестирования
        ↓
InstructionsWriteScenario.md →  Написание и отладка feature-файла
```

### Для сложного случая (многоагентный режим)

```
ПараметрыКонфигурации.MD → Заполнить пути проекта
        ↓
ТестПлан.MD → Описать все тесты в свободной форме
        ↓
ПодготовкаУправляющегоАгента.MD → Запустить оркестратор
        ↓
   (для каждого теста автоматически:)
   АнализДанныхИИнтерфейса → Исследователь → Код-Ревьюер →
   Писатель → Код-Ревьюер → ✅ Готово
        ↓
features/*.feature, research/*.MD, rewiew/*.MD, restore/*.MD
```

## Доступные инструменты:

Ниже приведена таблица всех доступных MCP инструментов Vanessa Automation, отсортированная по имени инструмента.

| Инструмент | Описание |
|------------|----------|
| **activate_process_os** | Активизирует окно процесса операционной системы: выводит его на передний план и передаёт ему фокус. Аналог шагов <И я активизирую процесс "PID"> и <И я активизирую процесс по заголовку "Заголовок">; полная аналогия с шагом по заголовку — при поиске с маской *заголовок*, без маски отбор шире — по подстроке. Нужно передать один из параметров: **pid** (положительное число; активизировать главное окно процесса) или **window_title** (найти процесс по заголовку или части заголовка окна; поддерживаются маски с *, например *Блокнот*; поиск без учёта регистра; маска проверяется на полное совпадение строки, поэтому для поиска по части строки оборачивайте выражение в * с обеих сторон). Параметры pid и window_title взаимоисключающие. Полезно перед всем, что работает с активным окном: эмуляция клавиатуры, ввод текста, шаги UI Automation, снятие скриншота. Для работы нужна включённая внешняя компонента VanessaExt. Не работает в веб-клиенте. Клиент тестирования не требуется. |
| **check_syntax** | Проверяет синтаксис Gherkin в указанном feature-файле. Параметр **filePath** обязателен; принимается только файл с расширением .feature (каталог и другие расширения отклоняются как INVALID_PARAMS и не меняют текущий каталог фич). Возвращает Markdown с найденными ошибками: неизвестные шаги, структурные проблемы, ошибки ключевых слов. Можно проверять любой feature-файл, даже если он не открыт в редакторе. Проверка оставляет проверяемый файл открытым и активным: если файл не был открыт, открывается новая вкладка; если файл уже открыт в редактируемой вкладке, она активируется; если только в diff-вкладке, создаётся редактируемая вкладка. Прежняя активная вкладка остаётся открытой. Текущим файлом фич становится проверяемый файл, поэтому последующие инструменты работают с ним. В Markdown-ответе указывается, изменилась ли активная вкладка, какая вкладка была активна до и после, была ли открыта новая вкладка и был ли файл открыт до проверки. При ошибке обработки результата загрузки или таймауте ожидания загрузки вкладка проверяемого файла не закрывается, а в текст ошибки добавляется фактическое состояние вкладок редактора. |
| **close_test_client** | Закрывает сеанс клиента тестирования по имени профиля. Если профиль не указан — закрывает текущий подключённый профиль. Используйте для завершения работы с клиентом тестирования после выполнения тестов. |
| **execute_feature_step** | Выполняет шаг из .feature файла по номеру строки. Если фича уже загружена, выполняет шаг без повторной загрузки; иначе загружает файл. Параметры **reload** (принудительная загрузка) и **details** (расширенный ответ: режим, номера строк, файл дерева). Внешние изменения файла на диске не проверяются. Если идёт загрузка, возвращает ACTION_FAILED с причиной BUSY — повторите вызов после её завершения. |
| **execute_form_actions** | Выполняет последовательность действий с элементами формы клиента тестирования. Позволяет выполнить несколько действий за один вызов инструмента. Параметр **actions_json** (обязательный) - JSON-строка с массивом действий. Каждое действие в массиве содержит: **action** - тип действия (click_button, input_text, и т.д.), **element_name** - имя элемента формы, **table_name** - имя таблицы (если элемент в таблице), **value** - значение для ввода/выбора, другие параметры в зависимости от действия. При возникновении ошибки выполнение прерывается. Ответ - компактный отчёт: одна строка на выполненное действие вида 'N действие адрес ok' (например, '1 set_value Менеджер=Admin ok ("Admin")'); полезная нагрузка read-действий (содержимое списка у get_dropdown_state, данные строк у get_selected_rows) и ошибки приводятся полным текстом. Модальные диалоги: диалог проверяется перед каждым действием, после последнего действия и при ошибке действия (диалог может появиться с задержкой - после цепочки асинхронных обработчиков). Появление модального диалога приостанавливает цепочку: результат возвращается со статусом paused_modal_dialog (это не ошибка), в нём - выполненные действия, текст диалога, его кнопки и машиночитаемый остаток цепочки (блок json), выполненные действия повторять не нужно. Диалоги не закрываются автоматически: ожидаемый диалог закрывайте действием **manage_modal_dialog** прямо в цепочке сразу после действия, которое его вызывает; неожиданный - ответом на паузу (**manage_modal_dialog** через **manage_form_elements**) и продолжением остатка. Окна 'Выбор типа данных' и 'Список значений' диалогами не считаются - с ними работает вызывающая сторона. После add_row на динамическом списке активна форма создания элемента: цепочку нужно остановить и продолжить после записи и закрытия формы; дальнейшие действия с этой таблицей в той же цепочке не выполнятся. Веб-клиент: не поддерживается. Требует подключённого клиента тестирования. |
| **find_form_elements** | Ищет элементы в активном окне клиента тестирования платформенным методом НайтиОбъекты: по заголовку, по имени элемента или по обоим (параметр **search_by**: all/title/name; по умолчанию all). Символ * - маска (например, *Товар*). Для каждого найденного элемента выводится заголовок, внутреннее имя, тип и вид, родитель первого уровня, а также имя табличной части, если элемент находится в таблице (учитываются колонки, вложенные в группы внутри таблицы). Параметр **search_string** обязателен; **limit** ограничивает число элементов в ответе (по умолчанию 50, 0 - без ограничения). Поиск идёт только по активному окну; элементы на ещё не открытых закладках (страницах формы) могут не находиться - переключите закладку (страницу) (**switch_tab**). Пустой результат - не ошибка. Требует платформы 8.3.25 и выше и подключённого клиента тестирования. Это поиск элементов формы клиента тестирования (не путать с **find_elements** UI Automation в **manage_uiautomation**). |
| **frequently_used_steps** | Возвращает информацию о том какие шаги чаще используются по статистике больших проектов. В начале идут часто используемые шаги, далее идут более редко используемые шаги. Возвращает представление шага, описание шага, тип шага. Также возвращает информацию сколько всего шагов есть в накопленной статистике. |
| **get_active_form_element** | Возвращает идентичность активного элемента формы клиента тестирования в модели TestClient: клиент, окно, форма, элемент (имя, заголовок, тип, вид), а для таблицы - таблица, текущая колонка (если определена) и сведения о выделенных строках. Read-only: не перемещает фокус, не открывает формы и не выполняет шаги. Если элемент не в фокусе или активное окно не является формой, возвращается явное пустое состояние, а не ошибка. Ответ - Markdown и блок JSON; **element_id** имеет вид `<ИмяФормы>/<ИмяЭлемента>` или `<ИмяФормы>/<ИмяТаблицы>/<ИмяКолонки>` (это идентификатор TestClient, не element_id UI Automation). При множественном выделении текущая строка может быть не определена, представление строки не формируется инструментом (row.selected_count > 1, row.representation = null); неопределённость текущей строки - поведение платформы. Требует подключённого клиента тестирования; при недоступности платформенного метода `ПолучитьТекущийЭлемент()` возвращается состояние unavailable с деталями. |

Если type=**form_name** - возвращает имя формы, подчиненной активному окну. Имя формы позволяет понять с каким объектом метаданных связано активное окно, т.к. в имени формы чаще всего содержится имя объекта метаданных. | **manage_variables** | Чтение, установка и удаление переменных тестового контекста. Действия с переменными: **get** (по умолчанию), **set**, **delete**. Переменные позволяют хранить произвольные значения в памяти Vanessa Automation. Переменные бывают локальные и глобальные. Локальные существуют во время выполнения сценария; движок очищает их перед штатным запуском сценария. При выполнении одного шага и запуске с текущего шага контекст может сохраняться. Глобальные переменные существуют пока работает Vanessa Automation и не удаляются перед выполнением сценария. Если переменная не найдена, **get** и **delete** сообщают об этом в ответе. Для **set** параметр **value** обязателен; пустая строка — допустимое значение. Параметр **is_global** для **get** с указанным **name** и для **delete** определяет, какой контекст использовать; **get** без **name** показывает оба контекста. |

Принимается только файл с расширением .feature (каталог не принимается). Используйте перед **check_syntax**, **execute_feature_step** и ручной навигацией по редактору. |

Текущая форма закрывается без подтверждения, несохранённые изменения редактора теряются; после перезапуска клиент тестирования нужно подключить заново. Требует установленного и включённого расширения VAExtension с обработкой VAExtension_ПерезапускVA в базе менеджера тестирования. Работает для Vanessa Automation и Vanessa Automation Single, открытых из файла .epf. |
| **run_scenario** | Запускает выполнение сценариев. Отправляет прогресс по каждому шагу (step N/M). Возвращает итоговый результат после завершения (при **wait**=true). Если указан **filePath** — загрузит фичу, откроет в редакторе и запустит. Режимы: **all** (по умолчанию — все сценарии; если просят выполнить все сценарии, используйте режим all), **reloadAndRun** (перечитать файл с диска и выполнить все его сценарии с начала), **selected** (выбранный в редакторе, перед этим надо вызвать **select_scenario**), **fromCurrentStep** (с текущего шага, перед этим нужно вызвать **select_step**), **reloadAndRunFromLine** (перечитать файл с диска и выполнить сценарий со строки **lineNumber**; параметр обязателен). В режимах **reloadAndRun** и **reloadAndRunFromLine** фича перечитывается с диска; точки останова не переносятся, так как номера строк могли измениться. **filePath** — только файл .feature, каталог не принимается. При **wait**=false в ответе возвращается идентификатор прогона (runId); он же доступен в **get_vanessa_automation_state** и **get_test_results**. |

Пример поиска шагов в представлении которых встречается слово "кнопка": **search_name** = "кнопка\|кнопки\|кнопку". Пример исключения шагов в описании которых встречается слово "гиперссылка": **exclude_description** = "гиперссылка\|гиперссылки". Пример поиска шагов в типе которых встречается строка "Объекты конфигурации": **search_type** = "Объекты конфигурации". Пример исключения шагов в описании которых встречается строка "Переменные среды": **exclude_type** = "Переменные среды". |

| **speak_text** | Синтезирует переданный текст в речь и произносит его пользователю настроенным движком синтеза речи (настройки берутся с закладки "Сервис" - "Автоинструкции" - "Аудио" - "Озвучивание диктором"). Параметр **text** обязателен и является массивом строк: при **no_play**=false массив должен содержать ровно одну фразу, при **no_play**=true - до 100 фраз (до 10 фраз синтезируются синхронно, больше 10 - пакетно с отправкой прогресса). Каждый элемент - до 500 символов; суммарная длина при синхронном синтезе - до 5000 символов, в пакете - до 50000. Полезно, чтобы голосом сообщить пользователю о завершении длинного задания, о необходимости принять решение или об ошибке. Во время воспроизведения другие MCP-инструменты доступны: плеер работает в отдельном потоке; ошибку возвращает только повторный **speak_text**, пока предыдущая фраза звучит. Синтез новой фразы синхронный и блокирует интерфейс Vanessa Automation, поэтому во время синтеза другие вызовы ждут. Параметр **wait** (boolean, по умолчанию false): если true, ответ возвращается после окончания воспроизведения фразы; действует только при no_play=false, при no_play=true игнорируется. Параметр **no_play** (boolean, по умолчанию false): если true, текст только синтезируется и сохраняется в кеш озвучки, без воспроизведения - полезно для прогрева кеша, последующий вызов с тем же текстом возьмёт озвучку из кеша без обращения к сервису синтеза. Прогрев требует включённого кеширования озвучки в настройках (Сервис - Автоинструкции - Аудио); в режиме обучения прогрев не работает. В режиме no_play при 10 и менее фразах ответ возвращается синхронно после завершения синтеза и может занять несколько секунд; при 11-100 фразах синтез идёт пакетно, ответ приходит после последней фразы, а при наличии токена прогресса отправляются уведомления. Ограничение "пока фраза звучит, повторный вызов возвращает ошибку" на no_play не действует. Требует включённую внешнюю компоненту VanessaExt. Не работает в веб-клиенте и под Linux. |
